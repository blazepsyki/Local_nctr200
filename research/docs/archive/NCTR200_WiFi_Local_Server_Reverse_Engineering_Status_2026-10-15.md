# 귀뚜라미 NCTR-200 WiFi 로컬 서버 전환 연구 기록

> **기록일:** 2026-10-15  
> **목표:** 기기 펌웨어를 추출·패치하지 않고, Wi-Fi 모듈의 서버 접속 설정을 변경하여 NCTR-200 WiFi가 제조사 클라우드 대신 사용자의 로컬 TCP 서버에 접속하게 만들고, 추후 Home Assistant(HA)에 통합한다.  
> **현 단계:** 운영 중 TCP 제어 프레임 분석 완료 / `krb_set` AP 연결·IP 통신 검증 완료 / 원격 AT **조회 응답 확보 실패** / 서버 주소 변경 **미실시**.

## 0. 사실과 추정의 구분

이 문서는 다음 표시를 사용한다.

- **[실측]** 사용자 제공 PCAPNG, Windows 명령 결과에서 직접 확인한 내용.
- **[코드]** 사용자 제공 디컴파일 APK Java 소스에 명시된 내용. 실제 기기에서 기능이 동작한다는 증거와는 구별한다.
- **[해석]** 실측 패킷과 APK를 대조해 상당한 근거가 있는 해석.
- **[가설]** 검증되지 않은 가능성. 설계 시 확정된 사실로 사용하면 안 된다.

특히 **기기에 실제 WizFi250 칩/펌웨어가 탑재되어 있는지**, **조회 AT 명령을 지원하는지**, **Flash 설정을 안전하게 덮어쓸 수 있는지**, **`AT+ABCD`의 의미**는 아직 확정하지 않았다.

## 3. APK 정적 분석에서 확인된 구조

### 3.1 앱 범위

- 패키지: `kr.openfloor.kituramiplatform.standalone` (구형 **귀뚜라미 IoT 매니저** Standalone 계열).
- 디컴파일 소스의 앱 버전: `2.8.9`(`BuildConfig.java` 기준). **기기 펌웨어 버전과 무관**하다.
- 멀티 매니저 `kr.openfloor.kituramiplatform.integrated`와 별도 앱이며, 이번 연구의 Java 코드 분석 대상은 Standalone이다.
- Java 소스는 제조사 서버 소스나 Wi-Fi 모듈 바이너리를 포함하지 않는다.

### 3.2 제어 경로

```text
스마트폰 앱 -- HTTPS REST (`device/deviceControl`) --> 제조사 서버
스마트폰 앱 <-- MQTT 구독(1883/TCP) --------- 제조사 측 상태 배포
NCTR-200       <--- 평문 TCP/20000 양방향 ---> 제조사 서버
```

**[코드]** 앱은 제어 명령을 HTTPS REST API로 송신하고, MQTT에서 `nodeId`를 토픽으로 사용해 상태를 수신한다. 분석된 앱 코드에서 **장치로 직접 TCP 소켓을 생성하는 정상 운용 경로는 발견되지 않았다.** 초기 설정에만 UDP 직접 통신이 있다.

- 운영 API 기준 주소: `https://igis.krb.co.kr/api/`
- 모델별 목적지 조회: `POST https://igis.krb.co.kr/modelUri`
- `modelUri` 데이터의 주요 필드: `modelName`, `ip`, `uri`, `rnum`
- 앱 MQTT: `iot-mqtt.krb.co.kr:1883` (앱의 클라우드 상태 수신 경로). **민감한 MQTT 인증정보는 문서에 포함하지 않는다.**
- 앱 코드에 `device/getServerAddress` 인터페이스도 있으나 실제 호출처는 확인되지 않았다.

주요 근거 파일: `DeviceAPIService.java`, `KituramiAPIController.java`, `modelUri.java`, `Setup.java`, `Control.java`, `MessageParser.java`, `MQTTController.java`.

### 3.3 `krb_set` 초기 프로비저닝 경로 — 가장 중요한 단서

**[코드]** `Setup_Step06.java`는 `NCTR-200 WIFI`를 분기 조건으로 명시하고 다음 명령들을 **하나의 UDP 데이터그램으로 이어 붙여 전송**한다.

```text
WizFi250AirCmd:AT+WSET=0,<SSID>\r
AT+WSEC=0,,<WiFiPassword>\r
AT+WNET=1\r
AT+SCON=S,TCN,<productIP>,20000,,1\r
AT+ABCD=S,TCN,<productURI>,20000,,1\r
AT+FSOCK=6,15\r
AT+MPROF=S\r
```

- 송신 목적지: **`192.168.200.1:20000/UDP`**.
- 이후 `UDPCommForRC.ReceiveMsg()`가 응답을 받으면 `WizFi250AirCmd:AT+MRESET\r`을 송신한다.
- `productIP`와 `productURI`는 앱의 `modelUri` 응답에서 유래한다.
- **NCTR-200 WIFI는 두 값이 서로 다른 필드로 사용되는 분기**에 속한다. 다른 모델에서는 두 인자가 동일 IP일 수 있다.
- `AT+SCON`은 표준 WizFi250의 TCP 소켓 자동 접속 관련 명령과 형태가 유사하다.
- `AT+MPROF=S`는 WizFi250 문서상 프로파일 저장 명령이다.
- **`AT+ABCD`의 기능은 미확인**이며, 공개 WizFi250 가이드와의 일치 여부가 확인되지 않았다. 보조 서버, 장애 복구 설정 등의 구체적 역할을 단정하지 않는다.
- `WizFi250AirCmd:` 문자열만으로 실물 모듈의 제조사/펌웨어를 최종 확정할 수는 없다.

**실험 설계에 중요한 차이:** 기존 Python 시험은 `WizFi250AirCmd:AT+MINFO\r`처럼 **단일 조회 명령**을 보냈다. 실제 APK의 성공 경로는 **여러 설정 명령을 하나의 데이터그램으로 보내는 방식**이다. 따라서 조회 명령 무응답이 프로비저닝 자체의 실패 가능성을 입증하지는 않는다.

`UDPCommForRC.java`는 응답 소켓에 타임아웃이 없고 데이터그램 객체를 재사용한다. 앱의 응답 판정 방식 자체가 견고한 검증이라고 보기도 어렵다.

### 3.4 앱 메시지 ID와 6바이트 본문

| ID | 의미 | 핵심 해석 |
|---|---|---|
| `0101` | 전원 | `roomID + 00000000 + state`; `01=ON`, `02=OFF` |
| `0102` | 실내난방 | 방 ID, ownerState, 현재온도, 온도모드, 목표온도, 소수필드 |
| `0103` | 난방 | 난방 설정/현재 온도 관련 |
| `0104` | 온돌 계열 | 온돌 설정/현재 온도 관련 |
| `0106` | 외출 | 방 ID + 외출 관련 상태 + 0 패딩 |
| `0107` | 일일 예약 | 30분 슬롯 × 48개의 방 비트마스크 |
| `0108` | 반복 예약 | 휴지·가동 시간 관련 |
| `0109` | 오류 | 오류 코드 관련 |
| `010A` | 실내 상태 | 현재 실내온도 등 |
| `0110` | 난방 상태 | 난방 온도 관련 |
| `0115` | 온수 온도 | 온수 설정값 관련 |

**[코드]** 이 명령 ID들은 원래 앱 REST/MQTT 계층에서 발견했다. 아래 실측 TCP 로그로 `0101`, `0102`, `0106`이 실제 장치 TCP에도 대응한다는 것이 추가 검증됐다. 나머지 ID가 반드시 동일하게 전달된다고 단정해서는 안 된다.

## 4. 제조사 TCP 통신 분석 (`packet_boiler.pcapng`)

### 4.1 연결 정보

| 항목 | 관측값 |
|---|---|
| 장치 IP | `192.168.137.156` |
| 서버 IP | `121.141.70.70` |
| 초기 서버 상태 확인 | **HTTP/80** |
| 주 제어 채널 | **TCP/20000** |
| 페이로드 형태 | 사람이 읽을 수 있는 TLS 암호화가 아닌 **평문 바이너리 응용 프레임** |
| 분석 시각 | 2026-10-15 20:26~20:32 KST 구간에 주요 이벤트 존재 |

초기 HTTP 요청:

```http
GET /serverConnectionNormalInfo HTTP/1.1
Host: igis.krb.co.kr
```

응답 JSON에서 관측된 부분:

```json
{
  "code": "100",
  "message": "Success.",
  "serverConnectionNormalInfo": { "uri": "D" }
}
```

**[실측]** 그 뒤 `121.141.70.70:20000`에 TCP 연결하고 세션 교환·상태 보고·앱 제어 명령을 처리했다. **[미확인]** HTTP 응답의 `uri=D`가 `AT+ABCD` 설정, 서버 우회, 서버 선택 등에 어떤 영향을 주는지는 아직 모른다.

### 4.2 관측된 TCP 응용 프레임의 공통 구조

```text
+-----------------+-----------------+------------------+--------------------+
| 명령 ID (2 B)   | 길이 (2 B, BE)  | 트랜잭션 ID (2 B) | 명령 데이터 (N B) |
+-----------------+-----------------+------------------+--------------------+
  offset 0~1         offset 2~3        offset 4~5         offset 6~

보통: 총 프레임 길이 = 4 + 길이 필드
      길이 필드 = 트랜잭션 ID 2 B + 명령 데이터 N B
```

- **[실측]** 여러 명령에 대해 위 구조가 성립하며, ACK는 보통 `[같은 명령 ID][00 02][같은 트랜잭션 ID]`의 6바이트 형식이다.
- **예외:** 초기 `0001` 서버 응답은 길이 필드가 `00 0B`인데 실제 뒤따른 데이터는 10바이트로 관측됐다. 따라서 **전 명령에 무조건 적용되는 완전한 프레이밍 사양은 아직 아니다.**
- TCP는 바이트 스트림이므로 패킷 하나가 메시지 하나라는 가정을 해서는 안 된다. 로컬 서버에서는 TCP 버퍼링·프레임 재조립이 필요하다.
- ACK 수신은 메시지 수신을 보여줄 뿐 실제 가스보일러 동작 완료·안전 상태를 보장하지 않는다.

#### 실측 예시 A — 앱에서 전원 OFF

```text
서버 → 기기: 01 01 00 08 C2 B8 01 00 00 00 00 02
기기 → 서버: 01 01 00 02 C2 B8
```

`01 01` = 전원, `02` = OFF, `C2 B8` = 요청·응답 대응 식별값.

#### 실측 예시 B — 앱에서 실내난방 목표 28°C

```text
서버 → 기기: 01 02 00 08 BD 55 01 00 00 00 1C 00
기기 → 서버: 01 02 00 02 BD 55
```

`1C` = 16진수 0x1C = 28. 이는 앱의 `MessageInner.java` 목표온도 위치와 대응한다.

#### 실측 예시 C — 외출 관련 상태/명령

```text
기기 → 서버: 01 06 00 08 92 D3 01 01 00 00 00 00
서버 → 기기: 01 06 00 02 92 D3

서버 → 기기: 01 06 00 08 17 AA 01 02 00 00 00 00
기기 → 서버: 01 06 00 02 17 AA
```

**중요:** 사용자 확인에 따르면 테스트 당시 **물리 조절기를 전혀 조작하지 않았다.** 따라서 `기기 → 서버`의 첫 `0106`은 물리 버튼 조작으로 인한 이벤트라고 해석하면 안 된다. 앞선 앱 명령으로 발생한 자동 상태 변화/보고 또는 내부 이벤트일 수 있다. `01`과 `02`의 사용자 UI 의미는 조작 시각과 추가 대조가 필요하다.

| 20:30:56 | 기기 → 서버 | `0106` | 기기 자체 외출 관련 이벤트/보고, 서버 ACK |

| 20:31:52 | 서버 → 기기 | `0106` | 앱 외출 관련 명령, 기기 ACK |
| 20:32:03 | 기기 → 서버 | `01FF` | 두 번째 대용량 상태 보고, 서버 ACK |

### 4.4 `01FF` 대용량 상태 보고

- **[실측]** 총 **109바이트**: 6바이트 헤더/트랜잭션 + **103바이트 데이터**.
- 약 **5분 1초** 간격으로 2회 수신했다. 2회만으로 일정한 5분 주기를 확정하지 않는다.
- 두 번째 데이터는 첫 번째와 비교해 세 위치가 달랐다.

| 데이터 시작을 0으로 본 바이트 오프셋 | 첫 번째 | 두 번째 | 의미 |
|---|---|---|---|
| `0` | `04` | `84` | 미확인 |
| `10` | `2A` | `29` | 미확인 |
| `90` | `01` | `02` | 미확인 |

온도, 난방 모드, 오류 또는 장치 상태가 포함될 가능성은 있으나 필드 정의가 확보되지 않았다. 추후 **한 번에 하나씩** 상태를 변경해 전후 메시지를 비교해야 한다.

## 5. 설정 AP 통신 분석 (`test.pcapng`)

### 5.1 AP 연결 및 IP 상태

```text
NCTR-200 WiFi 설정 AP
  SSID: krb_set
  장치 IP: 192.168.200.1
       │ Wi-Fi
       ▼
Windows PC: 192.168.200.2/24
```

**[실측]** 최초 Windows PC는 DHCP 임대에 실패하여 `169.254.0.102`(APIPA)를 사용했으나, Wi-Fi 어댑터에 `192.168.200.2/24`를 지정한 뒤 다음이 확인됐다.

- `ping 192.168.200.1`: **4/4 응답, 손실 0%, TTL 255**.
- `arp -a`: `192.168.200.1`의 MAC 주소 해석 성공.
- `test.pcapng`에는 **DHCP Offer/Request/ACK**도 존재한다. 즉 AP가 DHCP 서버를 전혀 제공하지 않는다는 이전 추정은 틀렸다. 최초 임대 실패 원인은 미확정이다.
- `krb_set`은 정상 인터넷 제공용 AP가 아니므로 인터넷 연결·기본 게이트웨이가 없더라도 설정용 로컬 통신에는 문제가 없다.

### 5.2 AT 조회 명령 송신 결과

Python은 각각 단일 UDP 데이터그램으로 다음 페이로드를 송신했다.

```text
WizFi250AirCmd:AT+MINFO\r
WizFi250AirCmd:AT+SCON=?\r
WizFi250AirCmd:AT+MPROF=VG\r
WizFi250AirCmd:AT+MPROF=VD\r
WizFi250AirCmd:AT+MAIRCMD=?\r
```

| PCAP 프레임 번호 | 목적지 | 조회 명령 | 응답 |
|---:|---|---|---|
| 431 | `192.168.200.1:20000/UDP` | `AT+MINFO` | 없음 |
| 433 | 동일 | `AT+SCON=?` | 없음 |
| 436 | 동일 | `AT+MPROF=VG` | 없음 |
| 440 | 동일 | `AT+MPROF=VD` | 없음 |
| 442 | 동일 | `AT+MAIRCMD=?` | 없음 |

**[실측]** 전송 문자열은 PCAP 원문에서 확인했고, 조절기 → PC 방향의 해당 UDP 응답은 없었다. 따라서 원인은 단순한 Python 화면 출력 오류가 아니다. 하지만 **AP가 명령을 내부적으로 처리했는지/거부했는지는 알 수 없다.**

### 5.3 UDP 포트 거동

- **[실측]** Windows가 UDP **5351**로 보낸 일부 패킷에는 조절기에서 `ICMP Destination Unreachable / Port Unreachable`을 반환했다.
- **[실측]** 반면 위 UDP **20000** 조회 패킷에는 UDP 응답도 없고 ICMP Port Unreachable도 관측되지 않았다.
- **[해석]** 포트 20000이 제조사 전용 수신 경로로 취급될 가능성은 있지만, 패킷 폐기·방화벽 정책 등으로도 같은 현상이 나타날 수 있다. **포트가 열려 있다고 단정할 수 없다.**
- **[미시험]** `test.pcapng`에는 **TCP/50001, UDP/50001**에 대한 진단 결과가 없다. 이를 시험했다는 것으로 기재하면 안 된다.

### 5.4 현재 실패 원인 후보

| 가능성 | 근거 / 구분 방법 |
|---|---|
| 장치가 조회 명령에 응답하지 않는 전용 프로비저닝 구현 | APK는 초기 설정용 명령 *묶음*만 보낸다. `AT+MINFO` 등의 읽기 명령은 APK 사용 근거가 없다. |
| Air Command 처리 조건이 다름 | 별도 포트/전송 방식/명령 형식 확인 필요. |
| 실제 프로비저닝 포트 20000이지만 단독 조회 메시지를 무시 | 제조사 앱 초기 설정 패킷과 1:1 비교 필요. |
| 하드웨어/펌웨어가 표준 WizFi250과 다름 | 보드 부품 번호 또는 정상 프로비저닝 응답으로 확인 필요. |
| 현재 AP 초기화 상태에서 기존 프로파일 정보가 지워짐 | 설정 모드 진입 방식과 정상 앱 재설정 결과 확인 필요. |

**판단:** `krb_set` 네트워크·IP·ICMP는 정상이다. **실패 지점은 원격 AT 명령의 응답 또는 처리 조건이며, 서버 목적지 재지정 가능성을 부정하는 결과는 아니다.**

## 6. 앞으로 검증할 핵심 가설

### H1. 로컬 서버 목적지는 Wi-Fi 모듈 설정값으로 지정 가능하다

**근거:** APK가 사용자 SSID/비밀번호와 함께 `AT+SCON`, `AT+ABCD`, `AT+MPROF=S`를 전송한다. **검증 필요:** 모듈이 실제로 이 명령을 수용하고, 현재 설정을 교체하며, 재부팅 후에도 유지하는지.

### H2. 전체 펌웨어 추출 없이 기존 초기화 절차만 변형해 서버를 로컬로 전환할 수 있다

**근거:** 앱 자체가 `<productIP>`와 `<productURI>`를 동적으로 넣는다. **검증 필요:** `AT+ABCD`의 필드 의미 및 HTTP `/serverConnectionNormalInfo` 서버 조회와의 상호작용.

### H3. 로컬 TCP 서버가 초기 통신과 ACK를 재현하면 앱 명령과 유사한 기능을 수행할 수 있다

**근거:** 실제 TCP 명령·ACK·`01FF` 상태 보고가 평문으로 수집됐다. **검증 필요:** 세션 식별·장치 인증·상태 보고 전체 필드·타임아웃·재연결·시간 동기화·비정상 상태 처리.

### H4. 제조사 인터넷 없이 완전히 독립 운용 가능하다

**현재 근거 부족:** 초기 HTTP 조회, TCP 목적지 설정, 서버 장애 동작을 별도 시험해야 한다. 단순 DNS 재지정만으로 독립성이 보장되는 것은 아니다.

## 7. 권장 다음 실험 순서

> **원칙:** 원래 서버 설정/복구 경로 확보 → 읽기 전용 진단 → 로컬 TCP 리스너 준비 → 주소 변경 → 접속 여부 확인 → 제어 프로토콜 검증 순서. 실제 가스보일러의 연소·안전 제어 동작을 임의로 시험하지 않는다.

### 단계 A — 설정 AP의 포트·응답 확인 (설정 변경 없음)

1. 조절기를 `krb_set` AP 상태로 둔다.
2. Windows Wi-Fi 인터페이스가 `192.168.200.2/24`인지 확인한다. 메인 Ethernet은 유지해도 된다.
3. `192.168.200.1` Ping 및 ARP를 확인한다.
4. `TCP/50001` 연결 가능 여부를 **진단**한다. WizFi250 공개 문서의 일반적인 Air Command 사례와 비교하려는 시험일 뿐, 귀뚜라미 실기의 사용 포트라는 보장은 없다.
5. Wireshark로 **송·수신을 동시에 기록**한다. 조회 명령에 응답이 없다면 불필요한 반복 송신은 중단한다.

Windows 예시:

```powershell
Test-NetConnection 192.168.200.1 -Port 50001
```

Wireshark 표시 필터:

```wireshark
ip.addr == 192.168.200.1 && (udp || tcp || icmp)
```

### 단계 B — 원래 제조사 앱의 정상 프로비저닝 과정을 관찰

1. 제조사 앱으로 `krb_set`에 연결해 **정상적인 Wi-Fi 설정 과정**을 수행한다.
2. 장치에 전송되는 실제 UDP **데이터그램 경계, 문자열, 응답, 순서, 재부팅**을 기록한다.
3. 단일 AT 조회 명령과 APK의 **여러 AT 명령을 합친 1개 데이터그램**의 동작 차이를 비교한다.
4. PC가 같은 AP에 접속했다는 이유만으로 **스마트폰 ↔ AP의 유니캐스트 트래픽을 수집할 수는 없다**. 필요하다면 스마트폰 자체 캡처, 무선 모니터 모드 또는 별도 관찰 경로를 설계한다.
5. 실제 프로비저닝 시 전달되는 `productIP`, `productURI`와 정상 운용 캡처의 접속 IP를 비교한다. 원래 설정/복구 값을 기록한다.

### 단계 C — 변경 가능성을 확인한 다음 로컬 목적지 시험

- Windows 모바일 핫스팟을 유지한다면 초기 로컬 목적지는 **`192.168.137.1:20000`**이다.
- Ubuntu 홈서버로 직접 연결하려면 해당 시점의 **서버 LAN IP**와 방화벽·경로를 검증한다. 기존 PC의 공유 네트워크/Ubuntu LAN 주소를 혼동하면 안 된다.
- `AT+SCON`의 기존 항목 덮어쓰기/중복 추가 동작, `AT+ABCD`의 필요성, 프로파일 저장·재부팅 동작을 확인하기 전에는 변경 명령을 실행하지 않는다.
- 로컬 TCP 서버를 먼저 **수신 기록만 하는 형태**로 준비한다. 최초 연결·재연결·초기 프레임을 수집하고, 안전성이 확인되기 전까지 임의의 난방 명령을 송신하지 않는다.
- 테스트 실패 시 원래 제조사 서버 주소 및 정식 앱 프로비저닝 경로로 복구한다.

### 단계 D — 로컬 게이트웨이 개발

우선 구현 항목:

1. TCP 스트림 누적 버퍼와 프레임 길이 처리(초기 `0001` 길이 예외 포함).
2. `0000`, `0001` 초기 세션 교환 분석 및 재현.
3. `0002` 연결 유지/조회 처리.
4. `0101`, `0102`, `0106` ACK 및 기기 자체 송신 메시지에 대한 서버 측 ACK 규칙 검증.
5. `01FF` 상태 보고 디코딩(현재/목표 온도, 모드, 안전 상태를 별도 검증).
6. 세션 타임아웃, 중복 송신, 재전송, 전원 복구 및 네트워크 끊김 처리.
7. 검증 완료 후 Home Assistant MQTT Climate 또는 커스텀 통합으로 노출.

**Matter는 우선순위가 낮다.** 제조사 클라우드 독립적인 안정적 로컬 게이트웨이를 먼저 완성한 후 브리지로 확장하는 편이 합리적이다.

### 8.2 Wireshark 표시 필터

```wireshark
# 정상 운용 조절기 통신
ip.addr == 192.168.137.156

# 제어 TCP 페이로드만
tcp.port == 20000 && tcp.len > 0

# 설정 AP로 전송하는 Air Command
ip.addr == 192.168.200.1 && udp.port == 20000

# ICMP 포트 접근 거부
icmp.type == 3 && icmp.code == 3
```

위 항목은 **표시 필터**다. 재분석 가능성을 위해 처음부터 캡처 필터로 제한하지 말고, 저장 후 필터링하는 것이 좋다.

### 8.3 현재 결론을 바꿀 수 있는 다음 증거

- 원래 귀뚜라미 앱이 `krb_set`에 전송하는 **실제 정상 프로비저닝 패킷 + 응답**.
- 모듈의 **실제 부품 마킹/펌웨어 버전**과 원격 AT 명령 지원 범위.
- `AT+SCON`·`AT+ABCD` 설정의 현재 값 또는 제조사 `modelUri`의 응답 내 값.
- 로컬 TCP 서버로 바꿨을 때 **최초 접속 성공 여부**와 외부 HTTP 조회 의존성.
- 모드/온도/외출/예약을 각각 독립 조작한 **시각 기록 및 PCAP**.

## 9. 보안·안전·복구 유의 사항

- 초기 프로비저닝 명령에는 **Wi-Fi SSID 및 평문 비밀번호**가 포함될 수 있다. 패킷이나 로그를 외부에 공유하기 전 반드시 마스킹한다.
- 정상 운용 PCAP에는 장치 식별 데이터와 같은 시간대의 스마트폰 개인 통신이 포함될 수 있다. 전체 PCAP을 공개 저장소에 올리지 않는다.
- APK에 포함된 제3자 서버 자격 증명은 문서화·재배포하거나 제조사 시스템에 임의 사용하지 않는다.
- **`AT+MPROF=S`, `AT+MRESET` 등의 쓰기·재부팅 명령은 지금까지 사용자 실기에 실행하지 않았다.** 테스트된 것은 읽기 명령 UDP 송신뿐이다.
- 설정 AP로의 재진입 방법은 확보했지만, **출고 설정·기존 서버 주소가 유지되는지/초기화되는지는 별개 문제**다.
- 가스보일러 안전 제어는 제조사 시스템의 책임 영역이다. 로컬 프로토콜 구현 초기에는 **단순 연결/로그 수집을 우선**하며 안전 관련 응답값이나 실제 연소 제어를 추정해 변경하지 않는다.
- Windows Wi-Fi 인터페이스에 설정한 `192.168.200.2` 고정 IP는 실험 후 **DHCP 자동 할당으로 복원**한다.

## 11. 현 상태 한 줄 요약

**APK에서 서버 목적지를 설정하는 코드가 발견됐고, 실기 TCP 프레임도 확보했으며, `krb_set` 접근까지 성공했다. 다음 결정적 과제는 정상 제조사 프로비저닝의 UDP 요청·응답을 확보해 모듈의 설정 변경 방식을 검증하는 것이다. 서버 주소 변경과 클라우드 독립 운용은 아직 성공했다고 말할 수 없다.**
