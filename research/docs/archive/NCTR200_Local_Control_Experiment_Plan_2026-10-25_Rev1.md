## 1. 목적과 완료 기준

첫 목표는 **물리 조작 → 장치발 `0102`·`0106` → 후속 `01FF` → 해석한 상태**가 일치하는 기록을 확보하는 것입니다. 그다음 원격 `0102`가 실제 LCD와 상태 보고에 어떻게 반영되는지 확인합니다. 이 결과를 바탕으로 상태 파서와 명령 결과 처리를 구현합니다.

이번 단계에서 DNS 목적지, 제조사 HTTP 응답, `AT+SCON`·`AT+ABCD`, 펌웨어를 함께 바꾸지 않습니다. HA 통합, 페어링 구현, 완전 오프라인 시험은 별도 단계입니다. 잘못된 프레임·재전송·토큰 충돌 같은 오류 주입은 모의 소켓에서만 수행합니다.

| 구분 | 현재 근거 | 이번에 확인할 내용 |
|---|---|---|
| 기존 기록에서 확인 | DNS 우회 연결, `0001`·`01FF` 교환, 물리 목표온도 변화와 `0102` byte 4 대응 | 같은 조건에서의 재현성과 후속 `01FF` 대응 |
| 관측됐으나 미해결 | 원격 명령 ACK 후 이전 목표온도를 보고한 사례 | 실제 미적용, 지연 보고, 모드 의존성 등을 구분할 증거 |
| 가설 | `0102` byte 2가 현재온도, byte 1이 조작 주체 등과 관련 | LCD·방향·조작 순서와 대조하되 값의 의미를 미리 지정하지 않음 |
| 미해독 | `01FF` 필드, `0106` ON/OFF 값, `0001` 시간 응답 후행 2바이트 | 이번에는 상태 필드와 외출 값을 우선 분석 |

단계별 완료 기준은 다음과 같습니다.

1. 모의 시험에서 프레임 재조립과 명령 차단 조건을 확인하고, 현재 결함과 향후 요구사항을 구분합니다.
2. 같은 설정을 유지한 기준선과 목표온도 왕복 조작의 자료를 확보합니다. 실험 구간에는 같은 TCP 세션의 변경 전후 `01FF`가 있어야 합니다.
3. 반복 관측에서 일관된 필드만 제한된 운전 모드의 상태로 해석합니다. 현재온도가 변하지 않아 검증할 수 없으면 미해결로 남깁니다.
4. 원격 시험에서 전송·ACK·LCD·상태 보고를 별도로 판정합니다. ACK만으로 적용 성공을 기록하지 않습니다.
5. 확보한 자료를 외부 네트워크나 실물 장치 없이 다시 분석해 같은 결과를 얻습니다.

## 2. 현재 코드로 가능한 것과 선행 개발

### 2.1 현재 v4로 가능한 시험

- `handshake` 모드에서 초기 교환·상태 수신·일부 장치발 이벤트 ACK를 수행할 수 있습니다.
- `--trace-state`로 `01FF` body와 직전 보고 대비 차분을 출력합니다. 차분 기준은 현재 연결의 직전 보고이며, 재연결 전 자료와 자동 비교하지 않습니다.
- 장치발 `0102`·`0106`의 6바이트 body와 토큰을 기록합니다. 일반 RX 로그는 body가 8바이트 이하일 때만 전문을 출력합니다.
- `status`, `wait 30`, `quit`를 사용할 수 있습니다. `wait N`은 최대 120초이며 아래의 12분 관측을 대신하지 않습니다.
- 준비 상태와 `--enable-temperature` 및 CLI의 `SEND` 확인을 거쳐 온도 명령을 보낼 수 있습니다.

`handshake` 모드는 응답을 송신합니다. 아래에서 말하는 수신 중심 시험은 온도 제어를 끈 시험이며, 네트워크상의 완전한 수동 관찰과는 다릅니다. `observe`는 응답하지 않으므로 정상 세션을 유지하며 상태를 분석하는 E01~E04의 기본 모드로 사용하지 않습니다.

### 2.2 정식 반복 시험 전에 보완할 기록 기능

현재 v4의 텍스트 로그와 수동 기록으로 예비 실험은 가능합니다. 다음 기능은 **아직 없으며**, 정식 회귀 시험 전에 구현할 대상입니다. 이 문서는 해당 옵션이나 도구가 이미 존재한다고 가정하지 않습니다.

| 보완 대상 | 요구사항 | 확인 방법 |
|---|---|---|
| 구조화 기록 | `run_id`, `session_id`, 세션 내 순번, KST 시각, 단조 증가 시각, 방향, ID, 토큰, 선언 길이, 실제 body 길이, body를 기록 | 모의 RX/TX와 저장 결과를 대조 |
| 물리 조작 표시 | 조작 전후 LCD 값·모드와 조작 시점을 같은 실행 ID에 연결 | 표시를 넣어도 추가 프로토콜 송신이 발생하지 않는지 확인 |
| 정보 보호 | `0001`의 전체 식별자는 공유용 로그에서 마스킹하고, 분석에 필요한 상태 body와 구분 | 고정 합성 ID로 저장본·오류 로그 검사 |
| 오프라인 분석 | 저장된 프레임·조작 기록에서 시계열·차분 표 생성, 장치 접속·명령 송신 없음 | 소켓 연결 없이 같은 입력을 두 번 분석해 결과 비교 |
| 저장 실패 감지 | 파일 쓰기 오류를 명시하고 기록 실패 이후 새 제어 명령을 차단 | 모의 저장 실패로 검증 |

세션 ID는 실행마다 달라질 수 있는 로컬 식별자입니다. 단조 증가 시각은 같은 프로세스 내 순서·경과 시간 계산에 사용하고, 서로 다른 PC의 값끼리 비교하지 않습니다. 실제 장치 ID로 세션 ID를 만들지 않습니다.

### 2.3 판정 시 주의할 현재 구현

- `ready=True`는 현재 연결에서 `0001`과 `01FF`를 처리했다는 뜻입니다. `01FF` body가 정확히 103바이트인지, 상태 의미가 유효한지까지 검사하지 않습니다. 실기 진입 시 로그에서 길이도 별도로 확인합니다.
- `send_temp()`는 최근 수신이 오래됐는지를 검사하지 않습니다. 연결이 살아 있다는 사실만으로 상태가 최신이라고 판정하지 않습니다.
- `pending`에는 응답 타임아웃·자동 재전송 처리가 없습니다. 관찰 기한은 실험자가 관리합니다.
- `(ID, token)`이 `pending`과 일치하면 body 유무와 관계없이 명령 응답 분기로 들어갑니다. 비어 있는 body의 ACK와 상태 이벤트를 구분하는 검증이 필요합니다.
- `--bootstrap-node-id`로 응답한 `0000` TX에는 전체 ID가 텍스트 로그에 남을 수 있습니다. 원본 로그·PCAP은 비공개로 보관합니다. 최신 `0001` 직행 경로에서는 이 옵션을 사용하지 않습니다.

## 4. 준비와 기록 저장

### 4.1 시작 조건

1. 조절기가 AP 설정 화면이 아닌 정상 운용 상태인지 확인하고, 전원·운전 모드·현재온도·목표온도·외출 표시를 기록합니다.
2. 기존에 성공한 DNS 우회 구성을 유지합니다. 실제 Ubuntu LAN IP와 서버에서 보이는 조절기 접속 IP를 확인합니다. 과거 기록의 `192.168.1.35`를 그대로 사용하지 않습니다.
3. TCP/20000을 쓰는 기존 시험 서버를 확인해 하나만 실행합니다. 같은 조절기에 앱·HA·다른 사용자가 동시에 명령을 보내지 않도록 합니다.
4. 서버 시각과 LCD 촬영·수동 기록 시각의 차이를 확인합니다. 차이를 확인할 수 없다면 같은 PC 시각을 사진에 함께 담고, 조작 시점의 오차 범위를 기록합니다.
5. 조절기에서 즉시 원래 설정으로 복구할 수 있는 상태에서만 물리·원격 조작을 진행합니다. 원래 설정과 복구 경로를 기록하지 못하면 E02 이후를 진행하지 않습니다.

### 4.2 저장 규칙

새 실험 자료는 `Boiler_IoT/experiments/<run_id>/`에 모읍니다. 이 경로는 시험 실행 시 생성하며, 이번 문서 작성에서는 만들지 않았습니다. 파일명은 영문으로, 기록 문서는 한국어로 작성합니다.

| 파일 | 내용 | 생성 시점 |
|---|---|---|
| `environment.txt` | 시각, Python 버전, 소스 해시, IP·인터페이스·DNS 구성 | 시험 시작 전 |
| `server.log` | 현재 v4 텍스트 로그 | 서버 실행 중 |
| `observations.md` | 실제 조작·LCD·시간 오차·복구 확인 | 사용자가 기록 |
| `session.pcap` | 해당 조절기와 서버 사이 TCP/20000 원본 | 캡처 도구 사용 시 |
| `events.jsonl` | 구조화된 프레임·표시 기록 | 기록 기능 구현 후 |

| `result.md` | 결과, 근거, 미판정 사유, 후속 과제 | 시험 종료 후 |

원본 PCAP과 로그에는 전체 ID 등이 들어갈 수 있습니다. 로컬 원본과 외부 공유용 마스킹 사본을 구분합니다. 합성 자료를 실기 자료에 섞지 않습니다. 아래 셸 명령은 **Ubuntu Bash, `Boiler_IoT` 루트 기준**이며 IP 자리표시자는 실측 값으로 교체합니다.

```bash
umask 077
export RUN_ID="$(TZ=Asia/Seoul date +%Y%m%d-%H%M%S)-physical"
export RUN_DIR="experiments/$RUN_ID"
export NCTR_SERVER_IP='REPLACE_WITH_SERVER_LAN_IP'
export NCTR_CLIENT_IP='REPLACE_WITH_OBSERVED_CLIENT_IP'
mkdir -p "$RUN_DIR"
{
  TZ=Asia/Seoul date --iso-8601=seconds
  python3 --version
  sha256sum src/nctr_local_autoid_server_v4.py
  ip -4 -o addr show
  printf 'server_ip=%s\nclient_ip=%s\n' "$NCTR_SERVER_IP" "$NCTR_CLIENT_IP"
} > "$RUN_DIR/environment.txt"
ss -lnt 'sport = :20000'
```

기존 DNS·방화벽 구성과 실험 전 LCD 상태는 `observations.md`에 추가합니다. `ss`에 기존 리스너가 보이면 소유 프로세스를 확인하고 중복 실행을 해소한 후 진행합니다.

```bash
set -o pipefail
python3 -u src/nctr_local_autoid_server_v4.py \
  --bind "$NCTR_SERVER_IP" --port 20000 \
  --mode handshake --time-tail 0123 \
  --allowed-client-ip "$NCTR_CLIENT_IP" --trace-state \
  2>&1 | tee "$RUN_DIR/server.log"
```

`0123`은 이전 시험을 재현하기 위한 미해독 값입니다. 유효한 표준값으로 확정하지 않습니다. 이 단계에서는 `--enable-temperature`, `--pair-code`, `--save-node-id`, `--bootstrap-node-id`를 추가하지 않습니다. `0000`만 반복되면 별도 문제로 기록하고 중단하며, 불명확한 ID를 만들어 응답하지 않습니다.

다른 터미널에서 필요한 경우 실제 LAN 인터페이스로 TCP 캡처를 시작합니다. 서버 접속 전부터 수집하려면 캡처를 먼저 시작합니다. `RUN_DIR`와 IP 변수는 다른 터미널에도 같은 값으로 설정해야 합니다.

```bash
export NCTR_CAPTURE_IFACE='REPLACE_WITH_LAN_INTERFACE'
sudo tcpdump -i "$NCTR_CAPTURE_IFACE" -s 0 -U \
  -w "$RUN_DIR/session.pcap" \
  "host $NCTR_CLIENT_IP and tcp port 20000"
```

이 필터는 TCP 프로토콜 분석용입니다. DNS·HTTP 경로와 완전 오프라인 동작을 검증하는 자료로 사용하지 않습니다. 원격 셸의 `temp N`·`SEND` 입력은 `tee` 로그에 모두 남는다고 보장할 수 없으므로 수동 기록과 TX 로그를 함께 보존합니다.

## 5. 로컬 모의 시험

테스트 하네스는 아직 없습니다. 구현 시 Python 표준 라이브러리의 `unittest`와 `socket.socketpair()` 또는 loopback 임시 포트를 사용합니다. 수신 소켓을 직접 넘기는 방식이 우선이며, 리스너가 필요하면 `127.0.0.1`과 임시 포트만 사용합니다. 모듈 import 과정에서 시간대 데이터가 없으면 환경 오류로 기록하고 먼저 해결합니다.

고정 합성 ID `1020304050607080`과 고정 토큰을 사용합니다. 모의 장치는 실제 보일러로 라우팅하지 않습니다. 날짜시간 응답은 고정 시계로 검사하거나 시간 범위를 검사하고, 실행 시각이 다르다는 이유로 바이트 일치 시험을 실패시키지 않습니다.

| ID | 입력·상황 | 검사할 결과 | 현재 코드에 대한 취급 |
|---|---|---|---|
| T01 | 정상 `0001`과 103바이트 `01FF`를 각각 매 바이트 경계에서 분할해 전달, 완전한 프레임 전에는 입력을 멈춰 중간 상태 확인 | 미완성 프레임을 처리하지 않고, 완성 뒤 한 번만 처리. 합쳐서 보낸 두 프레임도 각각 한 번 처리 | 현재 동작 검증 |
| T02 | 선언 길이 0·1·2049, 중간 EOF, 남은 body 부족 | 잘못된 길이는 연결 종료, 미완성 데이터로 상태 업데이트·준비 상태·추가 송신이 발생하지 않음 | 실물에 오류 입력 금지 |
| T03 | `0001` body 길이 7·9, ID 불일치, 정상 8바이트, `0000` 4바이트 요청과 bootstrap 없음 | 잘못된 ID로 학습하지 않음. 불일치 시 종료. `0000`만으로 전체 ID를 생성하지 않음 | 현재 동작 검증 |
| T04 | `0001` 전·후 각각 0·102·104바이트 `01FF` 전송 | 요구사항: 비정상 상태 보고로 명령 준비 상태를 만들지 않음 | **현재 v4는 길이를 검사하지 않아 실패 예상. 수정 전 통과로 기록하지 않음** |
| T05 | 제어 비활성, 준비 전, 연결 종료 후, 범위 밖, CLI에서 `SEND` 외 입력 | `0102` TX 0회. 정상 조건과 명시적 `SEND`에서만 1회. 취소·재연결 뒤 지연 명령 없음 | v4의 직접 메서드와 CLI 경로를 모두 검사 |
| T06 | 정상 명령 후 같은 ID·token의 빈 body ACK, 다른 토큰 ACK, 같은 토큰의 비어 있지 않은 상태 body | 요구사항: 일치하는 빈 ACK만 수신 확인. 상태는 별도로 처리하고 실제 적용은 미확정 유지 | **비어 있지 않은 body의 구분은 현 v4 보완 대상** |
| T07 | 정상 연결 종료 후 새 세션 생성, 연결 유지 중 수신 시각이 오래된 상황 | 새 세션은 재검증 전 준비 아님. 요구사항: 오래된 상태를 현재 상태로 표시하거나 제어 근거로 쓰지 않음 | 후반의 상태 신선도 정책은 미구현. 고정 모의 시계로 검증 |
| T08 | 103바이트 상태 원본과 body offset 16·32만 바꾼 합성 보고, ID가 포함된 RX/TX·오류 경로 | 차분 위치·전후 값이 정확하고, 합성 변화에 온도라는 의미를 자동 부여하지 않음. 공유 로그의 ID 마스킹 확인 | 실제 의미 검증과 분리. bootstrap TX의 기존 노출은 결함으로 기록 |

`0001` 서버 응답의 선언 길이 11·실제 후속 10바이트는 별도 회귀 자료로 보존합니다. 합성 시험이 이 응답을 재현한다는 사실은 프로토콜 사양이 옳다는 증거가 아닙니다. 오프라인 양방향 스트림 분석 시 방향·예외 조건을 명시하고, 임의로 모든 프레임에서 1바이트를 버리는 보정은 하지 않습니다.

T04·T06·T07·T08의 미구현 요구사항을 자동으로 성공 처리하지 않습니다. 현재 결과와 목표 결과를 나눠 기록하고, 수정 후 재실행합니다. 정상 길이·최근 수신·정상 모드가 수동으로 확인된 수신 중심 예비 실험은 가능하지만, 보호 조건이나 기록이 불명확하면 E05는 보류합니다.

## 6. 실물 시험 절차

### 공통 관측 시간과 판정 규칙

- 아래 시간은 **실험 운영을 위한 관찰 기한**이며 프로토콜의 확정된 타임아웃이 아닙니다.
- 연결 준비는 최대 120초 관찰합니다. 준비되지 않으면 해당 회차를 중단해 로그를 분석합니다.
- 각 조작 후에는 새 `01FF`를 받을 때까지 기다리되 최대 12분으로 제한합니다. 과거 약 301초 간격의 관측을 참고한 여유값이며, 12분 동안 보고가 없으면 상태 반영 실패로 단정하지 않고 자료 부족으로 기록합니다.
- 명령·조작 후 처음 60초는 이벤트와 LCD를 집중 기록하고, 이후에도 `01FF` 수신 또는 관찰 기한까지 기록을 유지합니다. LCD 확인 때문에 조작이 더 들어갔으면 추가 조작으로 기록합니다.
- 연결이 바뀌면 새 세션입니다. 이전 세션과 자동으로 차분을 연결하지 않고 E01의 기준선을 다시 확보합니다.
- body offset은 헤더와 token 6바이트를 제외한 body 시작을 0으로 셉니다. 길이 103의 `01FF`끼리 비교합니다.

### E01. 초기 연결과 무조작 기준선

1. 수신 중심 서버를 실행하고 CLI에서 `status`, `wait 30`, `status`를 확인합니다.
2. `CONNECTED → RX 0001 → TX 0001 → RX 01FF → TX 01FF`와 현재 연결의 `ready=True`를 기록합니다. 첫 `01FF` body가 103바이트인지 확인합니다.
3. 버튼·다이얼·원격 명령을 조작하지 않고 같은 세션의 `01FF`를 총 3개 모읍니다. 초기 준비 이후 최대 15분까지 관찰합니다.
4. 각 수신 시각, 보고 간격, body 길이, 변한 offset, LCD 현재·목표온도와 모드를 기록합니다. 자연 온도 변화도 기록합니다.

**성공 기준:** 같은 세션의 길이 103 보고 3개와 시각·LCD 기록을 확보했습니다. 이 단계의 성공은 모든 값이 고정돼야 한다는 뜻이 아닙니다. 무조작 중 변하는 바이트를 이후의 조작 효과와 구분하는 것이 목적입니다. 자료가 모이지 않으면 E02를 시작하지 않습니다.

### E02. 물리 목표온도 1°C 왕복 변경

1. 정상 실내난방 모드에서 원래 목표 `S`를 기록합니다. 기기의 지원 범위 안에서 `S`와 1°C 차이 나는 `S1`을 선택합니다. 26→27°C는 기존 사례일 뿐 이번 시험의 강제값이 아닙니다.
2. 새 `01FF` 기준선을 받은 뒤 다이얼로 `S → S1`만 변경합니다. 조작 직전·직후 시각과 LCD를 기록합니다.
3. 뒤따른 모든 `0102`의 6바이트, 토큰, 시각과 다음 `01FF`의 전체 body·차분을 저장합니다. 관찰 중 추가 명령을 보내지 않습니다.
4. 후속 `01FF`를 확보한 뒤 물리 다이얼로 `S1 → S`로 복구하고 같은 절차를 반복합니다. 보고가 없으면 기한 후 원래 설정을 복구하고 회차를 미판정으로 종료합니다.
5. 환경이 정상이고 기록이 완전할 때만 왕복 1회를 더 수행합니다. 총 2회 왕복에서 방향과 값의 대응을 확인합니다.

**필드 확인 기준:** body byte 4가 각 LCD 목표값과 맞고, `01FF` 후보 바이트가 두 차례 왕복에서 같은 값·방향으로 변하며 원래 값으로 돌아옵니다. 첫 회에서만 일치한 위치는 후보로 남깁니다. 복수의 위치가 함께 움직이면 모두 기록하고 실제 의미를 임의로 나누지 않습니다.

`ownerState`는 매번 원시값을 기록하되 `00=원격`, `01=수동` 같은 규칙을 미리 넣지 않습니다. 난방 시작에 따른 자연 실내온도 변화와 목표온도 필드를 혼동하지 않습니다.

### E03. 물리 외출 진입과 해제

1. E02를 종료하고 원래 목표·모드를 확인한 뒤 새 `01FF` 기준선을 확보합니다. 원래 외출 상태라면 먼저 그 사실과 정상 모드로 돌아오는 조작을 별도로 기록합니다.
2. 외출 버튼으로 외출에 진입하고, LCD·표시등 상태, 시각, `0106` 전체 body와 동반 `0101`·`0102` 등 모든 이벤트를 기록합니다.
3. 다음 `01FF`를 확보한 뒤 외출을 해제하고 같은 자료를 모읍니다. 외출 전후 목표온도도 함께 기록합니다.
4. 정상 모드·기준선 복구 후 한 번 더 반복합니다. 보고가 누락되거나 다른 조작이 끼면 해당 구간은 분리합니다.

**성공 기준:** 2회 진입·해제에서 실제 외출 표시와 같은 필드 값이 반복 대응합니다. 이벤트 ID만 대응하거나 값이 동일하면 ON/OFF는 미확정입니다. 이번 시험으로 서버발 외출 명령의 의미까지 확정하지 않습니다.

### E04. 현재온도 후보의 수동 관찰

1. 목표온도와 모드를 유지하고, 자연스러운 LCD 현재온도 변화가 있을 때 기록합니다. 시험을 위해 난방·센서·조절기에 외부 자극을 가하지 않습니다.
2. LCD 값과 `0102` byte 2 및 `01FF` 후보를 시각 기준으로 대조합니다. 방 온도계가 있다면 보조 자료로 기록하되 센서 위치·표시 정밀도 차이를 고려합니다.
3. 서로 다른 LCD 값 두 개 이상과 대응 보고를 확보하면 후보의 일관성을 평가합니다. 한 값만 유지됐거나 보고와 촬영 시각이 어긋나면 미판정입니다.

**성공 기준:** 관측한 복수 값과 보고의 대응을 설명할 수 있습니다. 이것만으로 센서 정확도·소수부·모든 운전 모드까지 검증됐다고 기록하지 않습니다. E04가 끝나지 않아도 검증된 목표온도 필드만으로 E05의 목표 반영 여부를 조사할 수 있습니다.

### E05. 원격 목표온도 한 번 변경

**진입 조건:** T01~T08 결과 검토, E01·E02 완료, 기록 누락 없음, 현재 정상 실내난방 모드와 최근 상태를 사용자가 확인한 상태입니다. 코드 변경이 있었다면 변경된 코드 해시와 모의 시험 결과를 새 실행 기록에 남깁니다.

1. 수신 중심 실행을 `quit`로 끝내고, E05용 새 `RUN_ID`·저장 폴더를 만듭니다. 이전 폴더의 로그를 덮어쓰지 않습니다.
2. 다음처럼 온도 제어 옵션을 추가해 실행합니다. 두 서버를 동시에 실행하지 않습니다.

```bash
python3 -u src/nctr_local_autoid_server_v4.py \
  --bind "$NCTR_SERVER_IP" --port 20000 \
  --mode handshake --time-tail 0123 \
  --allowed-client-ip "$NCTR_CLIENT_IP" \
  --enable-temperature --trace-state \
  2>&1 | tee "$RUN_DIR/server.log"
```

3. 새 연결의 `0001`·103바이트 `01FF`·`ready=True`와 LCD 기준선을 확인합니다. `status`의 최근 수신 시각도 확인합니다.
4. `S`와 1°C 차이 나는 `S1`을 선택합니다. 둘 다 실제 기기 지원 범위와 v4의 18~30°C 범위 안이어야 합니다. 만족하지 않으면 범위를 억지로 확장하지 않고 보류합니다.
5. CLI에 `temp S1`을 실제 숫자로 입력하고, 물리 조절기와 기록 준비를 확인한 뒤 `SEND`를 입력합니다. 예를 들어 `S1=23`이면 `temp 23`입니다. 한 번만 전송하고 실패해 보여도 재전송하지 않습니다.
6. TX의 토큰·body, 같은 ID·토큰의 빈 ACK, LCD 목표값·모드, 장치발 `0102`, 다음 `01FF`를 순서대로 기록합니다. ACK와 body가 있는 이벤트를 구분합니다.
7. 관찰 기한 또는 중단 조건에 도달하면 원래 목표·모드로 물리 복구합니다. 복구 시각 이후의 이벤트를 원격 명령의 반응으로 섞지 않습니다.

| 관측 결과 | 판정 |
|---|---|
| ACK + LCD가 `S1` + 검증된 상태 필드가 `S1` | 관측한 모드·조건에서 적용과 보고 일치 |
| ACK + LCD가 `S1` + 보고는 `S` | 적용 정황과 보고 불일치. 지연 시간·보고 종류·후속 스냅샷을 분석 |
| ACK + LCD가 `S` + 보고도 `S` | 관찰 기한 내 적용을 확인하지 못함. ACK 성공과 적용 성공을 분리 |
| ACK 없음 + LCD 또는 상태만 변경 | 통신·토큰 대응과 실제 적용을 별도 판정. 임의 재전송 금지 |
| LCD 미확인, 보고 누락, 중간 재연결·다른 조작 발생 | 인과관계 미판정. 확보된 사실만 남김 |

첫 회 결과를 검토한 뒤 필요할 때만 별도 실행 ID로 반복합니다. 모드·목표값·명령 body를 동시에 바꾸며 원인을 찾지 않습니다. `ownerState`별 명령 body 변형은 이 문서의 실물 시험 범위에 포함하지 않습니다.

## 7. 분석과 회귀 시험

### 분석 방법

1. 세션별로 TX·RX·물리 조작·LCD 기록을 시간순으로 배치합니다. TCP 재전송 패킷을 별도 응용 명령으로 중복 집계하지 않고 스트림을 재조립합니다.
2. 같은 세션·같은 길이의 `01FF`를 비교해 offset, 전후 값, 조작 종류를 표로 만듭니다. 보고 간격과 조작→보고 지연도 기록합니다.
3. 무조작 기준선에서 변한 위치를 표시합니다. 목표온도와 동시에 움직였다는 이유만으로 모두 목표 필드로 지정하지 않습니다.
4. E02의 왕복 반복 결과, E03의 토글 결과, E04의 관찰 결과를 각각 대조합니다. 명령 방향·운전 모드를 결과에 포함합니다.
5. 결론마다 원본 파일명·시각·프레임 또는 로그 위치를 연결합니다. 시각 오차 범위 안에 여러 조작이 있으면 인과관계를 미판정으로 남깁니다.

### T09. 확보 자료의 오프라인 회귀

분석 도구 구현 후 수행합니다. 입력은 마스킹된 실기 자료와 합성 오류 자료로 구분하고, 원본과 대응하는 비공개 매핑은 로컬에만 둡니다.

- 같은 자료를 두 번 분석해 같은 필드 값·차분·순서가 나오는지 확인합니다. 분석 실행 시각 같은 메타데이터는 비교 대상에서 제외합니다.
- 최소한 목표온도 왕복, 외출 진입·해제, 원격 명령과 보고 불일치 사례를 회귀 자료로 유지합니다. 확보하지 못한 사례를 만들어 실기 검증으로 표시하지 않습니다.
- 보류한 필드와 다른 운전 모드는 `unknown`으로 유지합니다. 합성 상태값을 실제 필드 의미의 증거로 쓰지 않습니다.
- 오프라인 재생은 파서·상태 모델에만 입력합니다. 저장된 TX를 장치 소켓으로 전송하는 기능은 두지 않습니다.

### T10. 명령 결과 상태 모델

상태 모델 구현 후 모의 시계로 검사합니다. 시험용 ACK 관찰 기한 10초와 적용 관찰 기한 12분은 설정 가능한 실험값이며, 프로토콜 사양이나 운영 기본값으로 확정하지 않습니다. 실제 장치에 자동 재전송하지 않습니다.

| 입력 순서 | 기대 결과 |
|---|---|
| 명령 전송만 발생 | 요청 목표와 마지막 장치 보고값을 별도 보관 |
| 일치하는 ACK만 도착 | 수신 확인. 실제 목표값은 아직 변경 확정하지 않음 |
| 검증된 보고가 요청값과 일치 | 장치 보고로 반영 확인. 실물 시험의 LCD 확인 여부는 별도 근거로 보관 |
| ACK 후 이전 값 보고 | 보고 불일치 유지. 이전 값을 지우거나 성공으로 덮어쓰지 않음 |
| 기한 내 확인 자료 없음 | 확인 시간 초과. 미적용이 입증됐다는 뜻으로 쓰지 않음 |
| 연결 종료·새 세션 시작 | 이전 pending을 새 연결의 응답으로 완료하지 않음. 마지막 상태의 신선도 무효화 |
| 다른 ID·토큰, 중복 ACK, body가 있는 같은 토큰 이벤트 | 다른 명령 완료로 오인하지 않고, 유효한 상태 이벤트는 별도로 반영 |

## 8. 중단과 원상복구

다음 상황에서는 새 원격 명령과 추가 조작을 중단합니다. 예상하지 않은 운전 모드·목표 변화, 오류 표시, 기록 중단, 잘못된 클라이언트 접속, 반복 재연결, 비정상 body 길이, 실제 상태를 확인할 수 없는 상황입니다. 타임아웃을 채우기 위해 불명확한 상태를 유지하지 않습니다.

1. 사람이 물리 조절기에서 원래 목표·모드를 확인하고 필요하면 즉시 복구합니다. 복구 시각을 기록합니다.
2. 서버에 `quit`를 입력하고 캡처를 종료합니다. 로그가 저장됐는지 확인합니다.
3. 로컬 경로의 상태가 불명확하면 기록해 둔 정상 DNS 구성을 복구하고 조절기의 정상 제조사 연결을 확인합니다. 공유기 전체나 보일러 전원을 임의로 끄는 시험은 포함하지 않습니다.
4. 공식 앱 재설정·등록이 필요한 경우 기존 인수인계의 복구 경로를 따릅니다. 원인 확인 없이 AP 초기화를 반복하지 않습니다.
5. 종료 후 LCD·모드·원격 연결 상태와 복구 결과를 `result.md`에 남깁니다. 실제 장치 오류는 실험을 계속해 원인을 추정하는 대신 정상 복구를 우선합니다.
