## 0. 가장 중요한 결론과 현재 상태

1. **[확인] 자체 DNS 리디렉션을 통해 NCTR-200이 사용자 Ubuntu 서버 TCP/20000에 실제로 연결했다.** 최신 로그에서 클라이언트 IP는 `192.168.1.35`(DHCP에 따라 바뀔 수 있음).
2. **[확인] 제조사 계정 미등록 상태에서도 `0001` 장치 식별, 서버 초기 응답, 103B `01FF` 상태 보고와 ACK가 작동한다.** 자체 서버에서 실제 장치와 세션 `ready=True`까지 성공.
3. **[관측] 자체 서버에서 전송한 `0102` 목표온도 명령을 장치가 동일 토큰의 ACK로 수신했고, 사용자는 28°C 명령 후 난방 운전 시작 및 다이얼 조작 결과를 통해 목표 설정이 적용된 것으로 판단했다.** 따라서 제조사 계정 등록은 **기본 TCP 제어의 선행 필수 조건이 아닌 것으로 강하게 뒷받침됨.** 단, 명령별·모드별 완전 검증은 아님.
4. **[확인] 물리 다이얼로 실내난방 목표를 26→27°C 변경했을 때 장치발 `0102`의 Byte 4가 `1A`→`1B`로 변경했다.** 현재온도 후보 Byte 2는 `1A`(26°C)로 유지. 사용자가 이 조작 순서를 명시적으로 확인함.
5. **[확인] 물리 외출 버튼 조작과 장치발 `0106` 메시지가 시간상 일치했다.** 다만 `0106` 내부 `01`/`02`가 활성/해제 중 무엇인지는 아직 미검증.
6. **[확인] 서버→장치 `0002` 응답의 등록 코드 첫 2바이트(Big-endian)가 실제 LCD의 `8667`, `3483`과 두 차례 일치했다.** AP Wi-Fi 설정 초기화 후 등록 코드 표시 실패도 사용자 관측. 등록 코드 기능은 **장치-사용자 소유권 연결을 위한 보안 페어링 기능으로 최종 구현에 포함할 계획**이며, 로컬 TCP 물리 제어를 성립시키는 기초 인증과 분리해서 설계.
7. **[미해결]** `01FF` 103바이트 상태 구조 전체, `0102` 원격 명령 이후 보고 지연/불일치, `0106` 외출 상태값, `0001` 응답의 미해독 2바이트 및 길이 예외, 제조사 `igis.krb.co.kr` HTTP 의존성 제거, 자체 프로비저닝, HA 통합.
8. **2026-10-19 실기 파일:** 현재 보관 경로 `src/archive/nctr_local_autoid_server_v4.py`(테스트용, **상시 운영 금지**). 코드 자체는 모의 소켓 시험을 거쳤고 실제 장치와의 `0001`/`01FF`/`0102` 상호작용이 실증됨. 버전 v4의 `--trace-state` 옵션은 실기에서 `01FF RAW` 출력을 확인했으며 **연속된 01FF 차분 검증은 당시 미수행**.

**현재 개발의 초점:** 연결·제어 가능성 검증에서 **물리 조작/원격 명령/상태 보고의 정확한 매핑, 신뢰성, 보안, 제조사 독립성**으로 이동.

## 2. Wi-Fi 초기 설정과 접속 대상 변경

### 2.1 정식 Android 앱의 프로비저닝 명령 — [소스 확인]

조절기 자체 AP는 `krb_set`, 기본 AP 주소는 `192.168.200.1`; 앱은 UDP/20000으로 다음을 **하나의 데이터그램**으로 전송한다. `\r`은 실제 CR 바이트이며, 비밀번호는 자리표시자다.

```text
WizFi250AirCmd:AT+WSET=0,<SSID>\r
AT+WSEC=0,,<WIFI_PASSWORD>\r
AT+WNET=1\r
AT+SCON=S,TCN,<productIP>,20000,,1\r
AT+ABCD=S,TCN,<productURI>,20000,,1\r
AT+FSOCK=6,15\r
AT+MPROF=S\r
```

설정 성공 후 별도 `WizFi250AirCmd:AT+MRESET\r` 송신. `productIP`, `productURI`는 앱이 제조사 `/modelUri` 응답에서 받은 값이며, 실제 한 로그에서는 `121.141.70.84`와 `http://igs4.krb.co.kr`이었다. 그러나 실기 TCP 연결 목적지는 당시 `121.141.70.70:20000`으로 관측됨. **`AT+ABCD`의 정확한 의미/우선순위는 미해결**.

### 2.2 DNS 방식이 먼저 선택된 이유와 실제 성과

- 원본 Wi-Fi 설정과 기기 펌웨어를 건드리지 않고 `igs4.krb.co.kr`의 A 응답만 Ubuntu 서버 IP로 변경한다.
- `igis.krb.co.kr`은 원본으로 유지해, 초기 HTTP 서버 선택 루틴을 바꾸지 않는다.
- **2026-10-18 23:22:56 KST**, 로컬 TCP 서버에서 `192.168.1.35:61989 CONNECTED`가 나타나 방식 자체가 작동함을 실증했다.
- 장기 목표는 DNS 조작 대신 **전용 프로비저닝**으로 `AT+SCON`·`AT+ABCD`의 서버 목적지를 로컬 IP/URI로 지정하는 것. 그러나 재부팅/완전 오프라인 유지 여부는 미검증.

### 2.3 조절기 AP 초기화와 등록 코드 표시 실험

- 조절기 **전원 OFF 후 외출 5초**: AP 설정 초기화(사용자 확인).
- 이어서 **전원 OFF 후 온수 5초**: 등록 코드 표시 시도했으나 표시되지 않음(사용자 관측).
- 해석: 코드 표시 기능에 네트워크 설정 또는 서버 연결 전제조건이 존재한다는 강한 단서. **단독으로 코드 생성 주체를 증명하지는 않는다.** TCP `0002`와 실제 표시값이 일치한 실험을 함께 사용해 판단해야 한다.

## 3. 제조사 앱의 기기 등록과 페어링 — 클라우드 전용 통제와 구분

### APK 정적 분석 — [소스 확인]

- `Register.java`: 앱은 사용자가 입력한 4자리 `authNumber`(`RegisterModel.productSerialNumber`)로 `device/registerDevice`를 호출하고, 성공 응답 `result`로 `nodeId` 문자열을 저장.
- `Login.java`: 계정의 기기 목록이 비어 있으면 `Setup`으로 이동; 기기가 있으면 해당 `deviceTopic`을 `nodeId`로 저장하고 `Control`로 이동.
- `Control.java`: 제어 화면은 저장된 `nodeId`로 MQTT 토픽 구독 및 제어 REST 요청을 생성.
- `ControlModel.java`: 제어에 사용되는 필드는 `nodeIds`, `messageId`, `messageBody`. **4자리 `authNumber`는 매 제어 명령에 들어가지 않음**.
- `Base.java`: `RequestDeviceControl()`에서 클라우드 `AUTH-KEY` 헤더와 함께 요청 송신.

**판정:** 제조사 **앱 UI/클라우드 계정**에서 등록은 제어 권한 부여에 필수이지만, **조절기 TCP 명령 수신을 위한 하드웨어 필수 인증과는 다른 계층**이다. 실험상 계정 미등록에서도 로컬 서버와 상태 교환 및 일부 물리 제어가 이루어졌다.

### `0002` 등록 코드 메시지 — [실기 + 패킷 확인]

```text
기기 → 서버: 00 02 00 02 [토큰 2바이트]
서버 → 기기: 00 02 00 06 [동일 토큰] [코드 BE 2바이트] 07 08
```

- 실험 1: `21 DB` = `0x21DB` = **8667**, 실제 LCD 값과 일치; 이후 앱에서 그 코드로 등록 성공.
- 실험 2: `0D 9B` = `0x0D9B` = **3483**, 실제 LCD 값과 일치; 별도 재등록 실험.
- 훨씬 앞선 PCAP의 `1F 14` = 7956은 **LCD와 대응 확인하지 않은 값**이므로 구분한다.
- `07 08` 의미와 코드 유효기간·저장 및 만료 처리 방식은 미해결. 임의로 TTL 1800초 등으로 단정하지 말 것.
- 신규 로컬 게이트웨이는 **사용자-장치 소유 관계 확인용** 등록 코드 방식을 보안 기능으로 설계할 것. `nodeId`는 평문으로 노출되므로 **그 자체가 인증 수단은 아님**.

**설계 후보:** 물리 조절기에서 등록 화면 진입 → 장치의 `0002` 요청 → 서버가 예측 어려운 일회용 4자리 코드 발급 → 조절기 LCD 표시 → 사용자가 HA/게이트웨이 화면에 코드 입력 → 기기 ID와 계정 바인딩 및 권한 부여. 짧은 만료, 단일 사용, 시도 횟수 제한, 재발급 무효화, LAN 격리, 관리자 권한 및 감사 로그 필요. **이 사용자 승인 절차는 미래에 구현할 것으로 합의했으며, 현재 시험용 `--pair-code`는 실제 보안 페어링을 구현하지 않음.**

## 4. TCP 프레임 구조와 확인된 메시지

### 4.1 기본 프레이밍 — [확인, `0001` 예외 있음]

```text
Offset  Size   Description
0       2      Message ID: big endian (예: 01 02)
2       2      Length: big endian, 보통 token 2B + body N B
4       2      Token / transaction ID
6       N      Body

일반 프레임 총 길이 = 4 + Length
ACK = [같은 ID 2B] [00 02] [같은 token 2B]
```

TCP는 스트림이므로 `recv()`가 프레임 경계와 일치하지 않는다. 현재 v4는 누적 버퍼로 재조립하고 `01FF` 103B 본문을 수신한다.

**`0001` 응답 예외:** 길이 필드는 `00 0B`이나 사용자가 제공한 실제 프레임은 헤더 뒤 **10바이트**(token 2B + 날짜시간 후보 6B + 미해독 2B)로 총 14바이트다. v4는 이전 PCAP을 모방해 `declared=11`과 실제 10바이트를 전송한다. 장치가 다음 `01FF`를 보냈으므로 **해당 실기에서는 응답을 적어도 초기 통신을 진행할 정도로 수락**, 정확한 표준 형식과 의미는 여전히 미확정.

### 4.2 식별/핸드셰이크

| ID | 방향 | 확인된 내용 | 남은 문제 |
|---|---|---|---|
| `0000` | 주로 장치↔서버 | 일부 과거 세션은 4B 식별 프리픽스로 시작, 서버가 8B ID 반환 | 항상 선행하는지 불확실. 이번 최신 실험은 `0001`부터 시작 |
| `0001` | 장치→서버 | 본문에 8B 고유 식별자. 등록되지 않은 상태에서도 전송 | 최초 응답 마지막 2B 의미, 길이 예외 |
| `0001` | 서버→장치 | 시간 바이트 후보 `YY MM DD HH MM SS` + 미해독 2B | `--time-tail 0123`은 임시 모방값 |
| `01FF` | 장치→서버 | 103B 상태 본문, 109B 전체 프레임. 초기 연결 시 전송. 과거 약 301초 간격 샘플 있음 | 전체 필드 미해독, 주기/이벤트 조건 미검증 |
| `01FF` | 서버→장치 | 6B ACK, 같은 토큰 | 장기 세션 유지 조건 미검증 |
| `0002` | 장치↔서버 | 요청/등록 코드 반환 | 코드 정책과 후행 `07 08` 미해독 |

**식별자 관련 주의:** 이전 정적 분석 보고서에는 `TYPE_NEW_200_BOILER="36"` 상수가 나오지만, 이번 실기 node ID의 마스킹 로그는 `3101:**********:AB`로 시작한다. 앱의 제품계열 상수 `36`을 실제 장치 node ID의 필수 접두사라고 가정하면 안 된다. 전체 ID는 사용자의 서버에 비공개로 보관한다.

**새 서버와 실기에서 성공한 초기 순서:** `CONNECT` → (수 초 대기) `RX 0001` → `TX 0001` → (~5초 뒤) `RX 01FF` → `TX 01FF` → `SESSION READY`. 장치 `nodeId`는 `0001`에서 서버가 자동 학습하며, **사전 계정 등록이나 사전 입력이 불필요했다**. 식별값 전문은 로그에 기록하지 않도록 마스킹; 필요하면 `--save-node-id`의 개인 파일에만 저장.

| ID | 역할 | 검증 수준 |

| `0102` | 실내난방 현재/목표온도, 모드 | **자체 서버 제어+ACK 실증, 물리 조작 시 상태 이벤트 실증** |

## 5. 최신 핵심 분석: 실내난방 `0102` 양방향

### 5.1 서버 → 조절기: 목표온도 설정

앱 `MessageInner.java`와 제조사 TCP PCAP의 일치 사례를 이용해 아래 6바이트 본문을 전송한다.

```text
01 00 00 00 1B 00   # 27°C
01 00 00 00 1C 00   # 28°C
01 00 00 00 1E 00   # 30°C (허용 가능 범위 별도 확인 필요)
│  │  │  │  │  └─ minor field
│  │  │  │  └──── target temperature
│  │  │  └─────── temperature mode
│  │  └────────── current field (명령에선 00)
│  └───────────── ownerState (명령에선 00)
└──────────────── roomID=1
```

전체 28°C TCP 프레임 예시(토큰은 매번 다름):

```text
01 02 00 08 42 0A 01 00 00 00 1C 00
```

ACK:

```text
01 02 00 02 42 0A
```

**이 ACK는 수신 확인**이지 LCD 목표값 변경의 자동 증명이 아니다. 그러나 2026-10-18 사용자 관측에서 28°C 명령 뒤 난방 운전이 시작됐고 목표가 변경된 것으로 판단됐다. **모드 전환을 포함하는 명령 적용 메커니즘**이 있을 수 있으나 그 조건은 미해결.

### 5.2 조절기 → 서버: 물리 다이얼 조작이 반영된 상태 이벤트 — [확인]

2026-10-19 00:07 시계열:

```text
00:07:35.827 RX 0102 token=380E body=01 01 1A 00 1A 00
00:07:44.048 RX 0102 token=57F2 body=01 01 1A 00 1B 00
00:08:06.498 RX 0106 token=AF08 body=01 01 00 00 00 00
```

사용자가 **실제 조절기에서 26→27°C로 다이얼을 돌린 후 외출 버튼을 누른 순서와 일치**함을 확인함.

| Body byte (0-based) | 첫 `0102` | 둘째 `0102` | 해석 |
|---:|---:|---:|---|
| 0 | `01` | `01` | room ID 1 — 고신뢰 |
| 1 | `01` | `01` | `ownerState` 원래 앱 변수명; 의미 미확정 |
| 2 | `1A` | `1A` | 현재 실내온도 **26°C 후보**, 앱 필드 구조와 일치 (물리 측정 교차확인 권장) |
| 3 | `00` | `00` | 온도 모드 세부 의미 미확정 |
| 4 | `1A` | `1B` | **실내난방 목표온도 26→27°C — 실제 다이얼 조작으로 검증** |
| 5 | `00` | `00` | 소수부 또는 보조값, 미검증 |

장치발 이벤트 수신 후 자체 서버가 동일 ID/token으로 ACK:

```text
01 02 00 02 38 0E
01 02 00 02 57 F2
01 06 00 02 AF 08
```

**추가 확인:** 2026-10-18 원격 `temp 27`, `temp 28`에 각각 같은 토큰의 ACK가 왔지만, 뒤따른 장치발 `0102`는 `01 00 1A 00 1A 00`을 보고했다. 이번 다이얼 이벤트 `01 01 ...`과 **Byte 1의 값이 다름**. `ownerState`가 이 차이를 설명하는지, 과거 값이 지연 보고됐는지, 실제 원격 명령이 어떤 내부 상태를 바꾸는지 **추가 패킷·LCD 동시 시험 필요**. `00=원격`, `01=수동`이라고 단정하지 말 것.

### 5.3 조절기 → 서버: 외출 `0106` — [이벤트 연관 확인, 방향/상태 미확인]

- 사용자가 `0102` 온도 변경 후 **물리 외출 버튼을 눌렀음**을 확인.
- 00:08:06.498 장치발 `0106` 본문: `01 01 00 00 00 00`.
- `0106`은 앱 소스에서 외출 관련 ID로 확인되며, 이번 로그와 실제 버튼 동작이 대응.
- **활성/해제 값의 의미는 아직 확정하지 않았다.** 최소 2회 연속 토글과 LCD 상태 기록이 필요.

## 6. `01FF` 전체 상태 보고: 최신 RAW와 확인할 오프셋

### 2026-10-19 00:07:08.199 — 최초 보고 (103B body)

```text
84 00 00 00 00 00 00 00 00 00 19 16 18 00 2D 3C
1A 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
1A 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
2D 3C 00 00 00 00 00 00 00 00 00 00 00 00 01 00
00 00 54 00 00 95 00 00 4E 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 01 00 01 00 00 00 00
00 00 00 00 00 00 00
```

표는 **body 시작이 0**인 오프셋임(헤더 6B 제외):

- `0=84`, `10=19`, `11=16`, `12=18`, `14=2D`, `15=3C`, **`16=1A`**, **`32=1A`**, `48=2D`, `49=3C`, `62=01`, `66=54`, `69=95`, `72=4E`, `89=01`, `91=01`. 모두 0이 아닌 값의 인덱스이며, **필드 의미는 원칙적으로 미해독**.
- 특히 `16`, `32`는 모두 26을 나타내지만 둘을 현재/목표온도라고 확정할 증거는 없음.
- 00:07:08의 보고는 00:07:35→00:07:44 다이얼 조작보다 **먼저** 도착했음. 따라서 이 `01FF`로 온도 변경에 대한 반응을 평가할 수는 없음.
- 이전 제조사 PCAP에서는 서로 다른 `01FF` 두 번 사이 약 301초(5분 1초)가 관측됨. 일정 주기인지 초기 이벤트 조건인지 추가 시험 필요.

**다음 실험:** `--trace-state` 상태에서 첫 `01FF` 기준선 확보 → LCD 값 정확히 기록 → **물리적으로 목표온도 1°C만 변경** → `0102` 이벤트 확인 → 다음 `01FF`의 `DIFF` 바이트 확인. 한 번에 모드/전원/온도 여러 조건을 변경하지 말 것. `01FF` 간격이 길 수 있으므로 충분히 관찰; 추가 제어 명령을 계속 보내지 말 것.

## 8. 현재 소스 코드와 실행 방법

### 8.1 과거 실기 재현 파일 — `src/archive/nctr_local_autoid_server_v4.py`

- Python 3 표준 라이브러리 사용(`zoneinfo` 등), 별도 pip 패키지 불필요.
- `--mode observe`: TCP 수신만 기록, 응답 없음(장치가 10초마다 `0001` 재전송할 수 있음).
- `--mode handshake`: 장치 식별, `0001` 시간 응답, `01FF` ACK, 기기발 일부 이벤트 ACK.
- `--save-node-id FILE`: 첫 `0001`에서 실제 8B ID를 **권한 0600 파일에 저장**; 콘솔에는 마스킹.
- `--bootstrap-node-id HEX`: 과거의 `0000` 선행 세션에만 선택적으로 필요. 최신 실험 `0001` 직행에는 불필요.
- `--allowed-client-ip 192.168.1.35`: 테스트 클라이언트 제한. DHCP 변경 시 수정. NAT 환경에 따라 보이는 소스 IP가 달라짐.
- `--enable-temperature`: 명시적으로 실험 명령 사용 허용.
- `--trace-state`: `01FF RAW`와 다음 보고 간 바이트 차분 기록.
- `--pair-code N`: 실험용 고정 코드 응답만 제공하며 **실제 페어링·인가 기능 없음**.
- 콘솔 명령: `status`, `wait 30`, `temp 27`, `temp 30`, `help`, `quit`. `temp N`은 18~30°C 범위, 준비된 세션에서만 전송, 사용자에게 `SEND` 재확인. **사용자 물리 조절기의 지원 범위와 안전을 최우선으로 할 것.**
- `ready` 조건: **동일한 현재 TCP 연결**에서 장치 `0001`과 `01FF` 모두 수신. 연결 전에 입력한 `temp`를 대기열로 보관하지 않음.
- v2의 `BrokenPipeError`는 `tee` 출력 종료 문제였으며 v4는 `emit()`에서 stdout 오류를 다루도록 개선.

#### 현재 상태 확인 (Ubuntu)

```bash
# 실제 LAN IP/포트/방화벽을 점검
ip -4 -o addr show dev enp3s0
sudo ss -lntup | grep -E ':53\b|:20000\b' || true

# 실험 TCP 서버 실행: 사용자의 실제 조절기 DHCP IP와 일치하는지 확인
python3 -u src/archive/nctr_local_autoid_server_v4.py \
  --mode handshake --port 20000 \
  --time-tail 0123 \
  --allowed-client-ip 192.168.1.35 \
  --trace-state \
  | tee nctr_trace.log

# CLI에서
#   status
#   wait 30
# 전송 권한은 --enable-temperature 없으면 차단된다.
```

#### 사람이 지켜보는 제한적 온도 제어 (다른 서버 인스턴스와 동시 실행 금지)

```bash
python3 -u src/archive/nctr_local_autoid_server_v4.py \
  --mode handshake --port 20000 \
  --time-tail 0123 \
  --allowed-client-ip 192.168.1.35 \
  --enable-temperature --trace-state \
  | tee nctr_control_trace.log
```

`status`에서 `ready=True`인지 확인 후 `temp N` 입력 → `SEND` 입력 → ACK와 **물리 LCD 목표값/운전 상태 및 뒤따른 장치발 이벤트**를 기록. 시험 후 원래 온도와 모드 복구. **상시 난방 제어용으로 서비스 등록하지 말 것.**

### 8.2 DNS 리디렉션: 실험에 사용된 로직(설정 재현 시)

현재 실제 DNS 구성이 동작하고 있다면 유지하고, 다음은 **재현용 예시**다. Ubuntu LAN IP는 `192.168.1.50`으로 가정한 **자리표시자**이므로 사용자 실제 값으로 교체해야 한다.

```bash
export NCTR_LAN_IP='192.168.1.50'  # 실제 서버 IP로 변경
sudo apt install dnsmasq-base
sudo dnsmasq --keep-in-foreground --bind-interfaces \
  --listen-address="$NCTR_LAN_IP" \
  --no-resolv --server=1.1.1.1 \
  --host-record=igs4.krb.co.kr,"$NCTR_LAN_IP" \
  --log-queries
```

- **조절기가 실제로 이 DNS를 사용해야 함**. PC의 `hosts`만 바꾸는 것으로는 보장하지 못함.
- `igis.krb.co.kr`은 바꾸지 않는 것이 기존 HTTP 의존성과 TCP 우회를 분리하는 데 유리.
- `ss`, `tcpdump`, DNS 질의 로그, 서버 `CONNECTED`로 실제 경로 확인.
- 이미 성공한 구성의 DNS/네트워크 설정값을 별도로 백업한 후에만 변경.

## 9. 해결되지 않은 기술 문제와 권장 다음 실험

### P0 — 안전하고 정확한 상태/모드 동기화 (가장 먼저)

후속 개발·시험은 [실험 계획 3판](NCTR200_Local_Control_Experiment_Plan.md)과 현장 절차를 따른다. 새 코드의 수집·세션·명령 처리·분석과 Windows 모의 시험을 구현했다. 전원·온돌·온수·예약·등록·복구의 기능별 검증은 계획에 따라 확장하며, 새 Ubuntu·실물 검증은 미수행이다. 이 인수인계의 과거 실기 판정은 유지한다.

1. **물리 조작 + `0102` 필드 확정:** 다이얼로 한 번에 1°C만 조정, LCD의 목표/실내 온도와 동일 시각의 TCP `0102` 각 필드 기록. 현재 Byte 4는 목표온도로 검증; Byte 2 현재온도는 물리 측정/표시와 추가 대응 확인.
2. **`0106` 외출 값:** 외출 버튼을 **ON → OFF** 각각 한 번씩 누르고 LED/LCD 모드, 원시 6B 본문, 추가 이벤트 (`0101` 등)를 함께 기록. 특히 `01 01 ...`, `01 02 ...`의 방향/의미를 시험 없이 미리 확정하지 말 것.
3. **원격 `0102` 후 상태 불일치:** 정상 실내난방 모드에서 원격 명령 1회, 앱/서버 ACK, 실제 LCD 설정, 장치발 `0102`, 외출/운전 모드 변화 시각을 순서대로 비교. 이전 사례는 원격 ACK 직후 나중에 수신된 이벤트의 Byte 4가 이전 목표 26°C를 보고한 적이 있다. **보낸 값으로 HA 목표 상태를 영구 확정해서는 안 된다.**
4. **`01FF` diff:** 5분 이상 모니터링하며 최초/후속 보고의 정확한 바이트 변경 오프셋 확인. 스냅샷 본문은 같은 세션의 103B를 비교. 장치 ID/기타 민감 데이터가 있을 수 있어 로그 외부 공유 주의.

### P1 — TCP 에뮬레이터 안정화

- `0001` 응답의 실제 길이 불일치와 마지막 2B 의미 해독. 서로 다른 시각/일자에 세션이 살아남는지 확인(현재 `0123` 고정).
- `0000` 시작 세션 대응(최신 시험은 `0001` 직행). 장치의 4B 프리픽스만으로 8B ID를 날조하지 않음.
- 메시지별 ACK 정책, 타임아웃/재전송, 상태 업데이트 이벤트, keepalive, 중복 명령, 토큰 충돌·상태 머신, 명령 실패 감지, 모드별 검증.
- **실제 난방/온수 안전 경계:** 임의 설정이 장치 내부 보호 기능을 우회한다고 가정해서는 안 되지만, 기기 제어 소프트웨어는 물리 운영 조건을 알고 명령을 제한해야 함.

### P1 — 등록 코드 기반 승인 및 로컬 게이트웨이 보안

- `0002` 요청에 실제 난수 기반 4자리 일회용 코드 발급, 물리 LCD 표시 연동.
- 계정/HA 관리자 승인, 장치 바인딩, TTL·최대 시도 횟수·중복 사용 방지, 등록 취소·재등록 정책.
- `nodeId` 평문만으로 접속 보안을 보장할 수 없으므로 IoT 네트워크 ACL/VLAN, TCP 20000 비공개, 상위 API 인증, 명령 권한 검증, 감사 로그.
- **중요한 설계 구분:** 물리 장치의 `0001` 식별자를 받아 프로토콜 세션을 성립시키는 것과 **사용자가 그 기기를 HA에서 제어하도록 권한을 부여하는 것**은 별개의 상태 머신이어야 한다.

### P2 — 제조사 완전 독립 및 프로비저닝

- DNS 우회가 성공했으므로, 다음은 `AT+SCON`/`AT+ABCD`를 로컬 서버 주소로 전용 프로비저닝하여 **DNS override 없이** 접속되는지 시험.
- `igis.krb.co.kr/serverConnectionNormalInfo`의 `uri:D`가 초기 연결에 필수인지, 완전 인터넷 차단 상태에서 재부팅 후에도 자체 서버로 복구 가능한지 시험.
- 정상 운용으로 돌아가는 공식 프로비저닝 복구 경로 보존. AP 초기화/등록 코드 재발급 절차 별도 보존.

### P3 — Home Assistant 통합

- **권장 아키텍처:** TCP 서버/상태 파서/명령 인가 계층을 HA 통합과 분리한 로컬 게이트웨이. 필요 시 MQTT 브리지 또는 HA 직접 통합.
- 실내난방 목표/현재온도, 운전/외출, 온수, 연결/오류, 주기적 상태 정합성을 별도 모델링. ACK를 실제 적용으로 오인하지 않기.
- `climate` 엔티티는 실제 실내온도/설정온도와 모드가 충분히 확인된 뒤만 노출, 다른 운전 방식(온돌/생활온수)은 별도 엔티티 또는 기능으로 구분.
- 안전한 기능을 작은 단위로 출시(모니터링 → 단일 setpoint → 외출 → 전원 → 온수/예약 순서).

## 10. 안전·보안·원상복구 원칙

- 실험 중 실제 조절기가 손에 닿는 범위에 있어야 하고, 현재 난방/목표온도/외출 상태를 사전에 기록한다. 실험 후 원상복구.
- TCP/20000, DNS/53, HA API, 임시 관리 웹 UI를 인터넷에 공개하지 말 것. Traefik 라우터/포트포워딩과 분리.
- `--enable-temperature`는 실험 시에만 명시적으로 활성화하며, 정상 상태에서 `status`/`--trace-state`와 같은 수신 중심 테스트 우선.
- 서버 ACK 수신은 물리 상태 변경의 증거가 아님. 변경 시점의 LCD 및 장치발 상태 이벤트를 함께 확인.
- 가스보일러의 연소 회로, 안전 센서, 배선, 장치 펌웨어를 수정하는 작업은 현재 범위 밖임.
- DNS 원상복구 → 조절기 Wi-Fi 재연결 → 제조사 서버 접속 및 필요 시 정식 재등록 → 물리 설정 복구 순서가 최우선 비상 복구 경로.
- Wi-Fi 암호, 전체 `nodeId`, 자격증명, 운영 MQTT 인증정보, 원본 Logcat 전문을 외부 게시/공유하지 말 것.
