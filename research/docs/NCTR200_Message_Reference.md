## 1. 프레임과 ACK

```text
ID 2B | Length 2B (Token부터 끝까지) | Token 2B | Body
ACK = 같은 ID·Token, Length 0002, Body 없음
```

- 조절기는 ACK를 받지 못한 이벤트를 3~5초마다 다시 보내고, 그동안 다음 이벤트를 보내지 않습니다(`0104`는 50분간 재전송, `0108`·`010A`도 같음). 반복되는 동안 본문은 최신 값으로 바뀝니다.
- ACK를 받으면 해당 이벤트는 다시 오지 않습니다(`field-20261121-11`에서 확인).
- 제조사 서버는 장치 이벤트에 모두 빈 본문 ACK를 보냈습니다. 수집 서버도 `0x0100~0x01FE` 이벤트에 기본으로 ACK합니다.
- 모드 버튼(난방·온돌·온수)을 누르면 값이 바뀌지 않아도 그 모드의 현재 설정을 한 번 보냅니다. 다이얼을 연속으로 돌리면 마지막 값만 옵니다.

## 2. 장치 → 서버

확인 = LCD 관측 또는 물리 조작과 대조함. 추정 = 기록과 맞지만 LCD로 확인하지 않음.

| ID | 기능 | 본문(6B) | 필드 | 수준 |
|---|---|---|---|---|
| `0000` | 부트스트랩 | `31 01 02 01` (4B) | 장치 유형 앞부분. 전체 ID 없음 | 10월 관측 |
| `0001` | 식별 | 8B 노드 ID | 서버가 시간으로 응답 | 확인 |
| `0002` | 등록 코드 요청 | 없음 | 서버가 `코드 2B + 07 08`로 응답 | 확인 |
| `0003` | 연결 확인(keepalive) | 없음(길이 2) | 5-1절 참고. 접속(`0001`) 60분 8초 뒤부터 60분 8초마다 10초 간격으로 반복. 서버 응답(빈 `0003`, 시간, `0001`)으로는 멈추지 않고, 조절기 이벤트나 서버 명령이 ACK로 오가면 멈춤 | 관측 |
| `0101` | 전원 OFF | `01 00 00 00 00 02` | OFF 때 02(11-20, 11-22 01:37:28). ON은 `0101` 없이 복귀한 모드의 보고(`0104` 등)로 옴 | 확인 |
| `0102` | 실내난방 | `01 SS CC 00 TT 00` | SS 출처(1=조절기 조작, 0=원격 명령 뒤 보고), CC 현재온도, TT 희망온도(10~45, 매뉴얼·실물 확인 2026-11-22) | 확인 |
| `0104` | 온돌 | `00 00 WW 00 OO 00` | OO 온돌 희망온도(45~85), WW 난방수 온도(=`01FF[10]`) | OO 확인, WW 추정 |
| `0105` | 목욕 | `00 00 00 00 3C 00` | 값 60. LCD의 80은 전송되지 않음 | 확인 |
| `0106` | 외출 진입 | `01 01 00 00 00 00` | 고정. 외출 중 다시 눌러도 같은 보고 | 확인 |
| `0108` | 난방 예약 | `01 00 00 00 HH MM` | HH 예약정지(시간, 1~24), MM 예약가동(분, 10~90). 예약 버튼을 누를 때마다 같은 보고가 옴. 가동·정지 순서를 바꿔도 본문은 같음 | 확인 |
| `010A` | 현재 실내온도 | `01 00 00 00 CC 00` | CC 현재온도. 현재온도가 바뀌면 조절기가 보냄. 11-21 23:39 LCD 23→22 때 22. 11-22 13:01:48 값 23 → 다음 `01FF[16]` 22→23, 16:15 LCD 23·`0102` 현재온도 23과 일치(`field-20261122-31`) | 확인 |
| `0114` | 온수 전용 | `00 00 00 00 HW 00` | HW 온수 설정(60). 난방 버튼 5초(11-22 01:18:53) | 확인(기능), 값 추정 |
| `0115` | 온수 설정 | `00 00 00 00 HW 00` | HW 온수 온도(35~60) | 확인 |
| `01FF` | 상태 보고 | 103B, 약 5분 간격 | 3절 | 확인 |

외출 해제는 별도 메시지가 아니라 새로 선택한 모드의 보고(`0102` 등)로 옵니다.

## 3. `01FF` 상태 보고 (103B)

|---|---|---|---|

| 11, 12 | 다른 온도 | 26~30, 29~36 | 추정 |
| 14 | 온돌 희망온도 | 45 | 확인 |
| 15 | 온수 설정 | 60 | 확인 |
| 16 | 현재온도 | 22~25 | 확인 |
| 32 | 실내 희망온도 | 26~28 | 확인 |
| 48, 49 | 고정값 | 45, 60 | 추정. 설정을 바꿔도 변하지 않음(`field-20261122-20`) |
| 58~59 | 16비트 값 | 0, 1500, 1560 | 추정(연소 관련) |
| 62 | 연소 단계 | 1, 2, 10 | 추정 |
| 66, 69, 72 | 누적 카운터 | 1씩 증가 | 추정 |

| 명령(CLI) | ID·본문 | 형식 근거 | 기본 범위 / 끄는 옵션 |
|---|---|---|---|
| `temp N` | `0102 01 00 00 00 NN 00` | 제조사 캡처, 실물 확인(11-22) | 10~45 / `--disable temperature` |
| `power on/off` | `0101 01 00 00 00 00 01/02` | 제조사 캡처, 실물 확인(11-22). OFF는 ACK, **ON은 ACK 없이 복귀한 모드의 보고**(`0104` 등)로 응답 → 서버가 이를 ON 확인으로 처리 | - / `--disable power` |
| `hotwater N` | `0115 00 00 00 00 NN 00` | 제조사 캡처, 실물 확인(11-22). 목욕 중에는 ACK만 오고 적용되지 않음(조절기가 `0105`로 응답) | 35~60 / `--disable hot_water` |
| `bath` | `0105 00 00 00 00 3C 00` | 제조사 캡처, 실물 확인(11-22) | - / `--disable bath` |
| `hotwateronly [N]` | `0114 00 00 00 00 NN 00` | `0114` 보고 형식, 실물 확인(11-22 22 회차). N 생략 시 현재 온수 설정 | 35~60 / `--disable hot_water_only` |
| `reserve H M` | `0108 01 00 00 00 HH MM` | 제조사 캡처(boiler6, 11-22), 실물 확인(22 회차). H 예약정지 1~24시간, M 예약가동 10~90분. 가동·정지 순서는 원격 지정 불가(앱도 항상 정지 먼저) | - / `--disable reservation` |
| `heatwater N` | `0103 00 00 00 00 NN 00` | 제조사 캡처(boiler6). 앱의 난방수·온수 동시 설정 화면이 `0115`와 함께 보냄. 이 명령은 `0103`만 보냄. 단독 전송 실물 확인(11-22 27 회차, 60) | 45~85, 1도 단위 / `--disable heating_water` |
| `schedule 구간` | `0107 01` + 30분 칸 48바이트 | 제조사 캡처(boiler6), 실물 확인(11-22 27 회차, 00:00-23:00). 예: `schedule 00:00-09:00,18:00-24:00`. 30분 단위, 칸 값 1=가동 | - / `--disable schedule` |
| `away` | `0106 01 02 00 00 00 00` | 제조사 캡처, 실물 확인(11-22). 해제는 `temp N` 등 모드 명령 | - / `--disable away` |
| `ondol N` | `0104 00 00 00 00 NN 00` | 제조사 캡처(boiler6), 실물 확인(`field-20261122-20`: 50→45, ACK·LCD·`01FF[14]` 일치) | 45~85 / `--disable ondol` |

CLI(`collect`)는 위 명령을 모두 켠 상태로 시작합니다. `--no-control`이면 전부 꺼지고, observe 모드에서는 항상 꺼집니다. 라이브러리 `Config`의 기본값은 모두 꺼짐입니다.

- 외출 해제는 원하는 모드의 명령(예: `temp N`)으로 합니다.
- 모든 명령은 `SEND` 확인 후 한 번만 보내며, 자동 재전송하지 않습니다. ACK와 장치 보고, 사용자의 `lcd` 관측을 따로 기록합니다.
- 실내 온도(`temp`) 명령 뒤에는 조절기가 `0102`(출처 0)로 보고합니다. 온돌·온수·목욕·외출 명령에는 ACK만 보내고 바뀐 값을 스스로 보고하지 않습니다(10월 제조사 캡처, `field-20261122-20·21`). 그래서 다음 `01FF`의 저장값(실내 `[32]`, 온수 `[15]`, 온돌 `[14]`)을 요청값과 대조해 `command_report_candidate`(`source=01FF[n]`)로 기록합니다. 전원·목욕·외출은 대응 필드가 확인되지 않아 LCD 관측으로만 판정합니다.
- ACK를 받은 명령은 다음 명령을 보내면 `command_superseded`로 끝나고 새 명령이 나갑니다. ACK 전에는 다음 명령을 막습니다.
- 난방 예약(`reserve`)의 `lcd` 관측은 `lcd <command_id> 3:20`(정지 시간:가동 분)으로 입력합니다. 앱 전용 24시간 예약은 형식 확인 전이라 구현하지 않았습니다.

### 제조사 앱 캡처(boiler6, 2026-11-22 02:50~02:53)에서 확인한 것

- 앱 명령 `0102`·`0104`·`0105`·`0106`·`0108`·`0115`는 이 서버의 명령과 본문이 같음. 그래서 조절기 보고에서 추정했던 `0104`·`0108` 형식이 제조사 형식으로 확인됨.
- 새 명령 2개: `0103`(난방수 온도, 앱이 `0115`와 한 쌍으로 보냄. 캡처에서는 5도씩 바꿨지만 1도 단위로 설정 가능), `0107`(24시간 예약, 49바이트: 방 마스크 `01` + 00:00부터 30분 칸 48개, 1=가동. 캡처 값은 00:00~09:00·18:00~24:00 가동으로 앱 설정과 일치).
- 조절기는 앱 명령에도 ACK만 보냄. 앱 예약 명령 27초 뒤 조절기가 `0108`로 예약 값을 보고함.
- 제조사 서버는 ACK가 늦으면 같은 토큰으로 0.4~0.7초 만에 재전송함. 이 서버는 재전송하지 않음(조절기 ACK는 보통 0.5~0.7초).

## 5. 신규 메시지 로그

수집 서버는 3절까지의 형식과 다른 메시지를 실행 폴더의 `novel.*.jsonl`에 따로 남깁니다. 원래 `events.*.jsonl` 기록은 그대로 둡니다.

| 사유 | 뜻 |
|---|---|
| `unknown_id` | 표에 없는 ID |
| `unexpected_length` | 알려진 ID의 길이가 다름 |
| `fixed_bytes_differ:i` | 고정이던 바이트가 다름 |
| `out_of_range:이름=값` | 매뉴얼 범위를 벗어남 |
| `new_value:이름=값` | 처음 보는 값(전원 등) |
| `state_constant_changed:i` | `01FF`의 고정 offset이 바뀜 |
| `new_status_flags:XX` | `01FF[0]`의 처음 보는 값 |
| `unconfirmed_message` | 형식만 알고 의미를 LCD로 확인하지 못한 ID(현재는 없음) |
| `unmatched_ack` | 서버가 보낸 적 없는 명령에 대한 ACK |

각 줄에는 원본 본문, 직전 marker, 같은 세션의 최근 프레임 6개, 대기 중 명령 ID가 함께 들어갑니다. NAS에서는 `nctr_novel 회차`로 보고, `analyze` 결과의 `novel_messages`와 `result.md`에도 요약됩니다. 확인된 새 형식은 `messages.py`의 표에 추가하고 이 문서를 고칩니다.

같은 ID·같은 사유가 반복되면 처음 5건만 자세히 남기고, 그 뒤로는 10·100·1000건째와 수집기 종료 때 누적 횟수(`novel_message_repeated`, `repeat_total`)만 남깁니다. `analyze` 요약의 횟수는 누적값을 씁니다. 11-22 30 회차에서는 응답하지 않은 `0003`이 `unmatched_ack`로 2,313줄(1.8MB) 쌓였습니다.

## 5-1. `0003` 연결 확인

| 회차 | 서버 응답 | 시작 | 끝 | 횟수 | 끝난 계기 |
|---|---|---|---|---|---|
| 30(boiler8) | 없음 | 05:17:02 | 수집 종료까지 | 2,409 | 없음 |
| 31 | 빈 `0003` | 13:01:37 | 13:01:47 | 2 | 조절기 `010A` 13:01:48 |
| 31 | 빈 `0003` | 14:01:45 | 16:15:42 | 803 | 조절기 `0102` 16:15:46(패널 모드 변경) |
| 33 | `probe` | 17:46:11 | 19:09:15 | 499 | 서버 명령 `0104`(온돌 45) 19:09:16, 조절기 ACK 19:09:18 |
| 33 | `echo` | 19:46:27 | 21:10:37 | 505 | 조절기 `010A` 21:10:49 |
| 33 | `echo` | 21:46:42 | 22:52:40 | 396 | 조절기가 연결을 끊음(22:52:46) |

- 시작 시각은 접속(`0001`) 시점에 고정된 60분 8초 주기입니다(30회차 04:16:54 → 05:17:02, 31회차 12:01:29 → 13:01:37 → 14:01:45, 33회차 16:46:04 → 17:46:11 → 19:46:27 → 21:46:42). 이전 반복이 이어지는 동안에는 새로 시작하지 않습니다(33회차 18:46, 20:46).
- 서버 명령은 시작 시각을 바꾸지 않습니다. 반복 전 명령(31회차 12:08)도, 반복을 멈춘 명령(33회차 19:09)도 다음 시작을 늦추지 않았습니다. 그래서 1시간마다 명령을 보내 반복을 미리 막을 수는 없습니다.
- 서버 응답으로는 멈추지 않습니다. 33회차 `probe`에서 `time`, `time6`, `identity`(`0001` 시간 응답)를 3회씩 보냈지만 10초 간격이 그대로였고, 연결 끊김이나 재접속도 없었습니다. 반복은 조절기 이벤트에 서버가 ACK하거나, 서버 명령에 조절기가 ACK하는 등 실제 메시지가 오갈 때 멈춥니다.
- 반복 중 `01FF`는 평소대로 5분마다 오고 연결도 유지됩니다(30회차 6.7시간).
- 제조사 서버의 응답은 아직 모릅니다. 제조사 서버와의 캡처(261017 약 151초, boiler6 약 164초)는 1시간보다 짧아서 `0003`이 나올 수 없었습니다.
- 반복은 해가 없어(30회차 응답 없이 6.7시간 유지) 수집기 기본값은 `echo`입니다.
- 수집기 `--keepalive-reply`
  - `echo`(기본): 같은 토큰의 빈 `0003`
  - `none`: 응답하지 않음(`--no-keepalive-reply`와 같음)
  - `time`: `0003` + `0001` 응답과 같은 8바이트(YYMMDDhhmmss + 시간 꼬리)
  - `time6`: `0003` + 날짜·시각 6바이트
  - `identity`: `0003`의 토큰으로 `0001` 시간 응답
  - `probe`: 한 번의 반복 안에서 `time`, `time6`, `identity`, `echo`를 3회씩 차례로 사용하고, 그 뒤로는 `echo`
- 기록: `keepalive` 사건(`reply`, `run_count`)과, 반복이 끝났을 때 `keepalive_run_end`(`count`, `last_reply`, `ended_by`). `ended_by`가 `gap`이면 마지막 응답 뒤 30초 넘게 `0003`이 오지 않은 것이고, ID이면 그 메시지(조절기 이벤트 또는 서버 명령 `0104` 등)로 끝난 것입니다. `gap`이면서 `last_reply`가 `echo`가 아니면 그 응답이 반복을 멈춘 후보입니다.

| 절약 모드 | 실내난방에서 난방 버튼을 다시 눌러도 절약 아이콘(S)이 켜지지 않고, `0113`(APK 절약 메시지)이나 다른 보고·상태 변화가 없음(11-21~22). 제조사 앱에도 없음 |
| 즉시 상태 요청 | 앱 새로고침 때 서버가 조절기에 보내는 메시지 없음(boiler6). `01FF`는 약 301초 주기와 접속 직후에만 옴. 서버가 먼저 `01FF`(빈 본문, 본문 `00`)를 보내도 조절기는 ACK도 보고도 하지 않음(32회차 16:30:26, 16:31:05) |
| 난방 예약 순서의 원격 변경 | 앱의 `0108`에 순서 정보 없음, 앱은 항상 정지 먼저. 순서는 조절기 예약 버튼으로만 바꿈 |
| 온수 학습 | 외출 5초에도 아이콘이 켜지지 않음(11-21 23:33) |
| 가스 사용량의 원격 조회 | 조절기 화면 안에서만 동작, 통신 없음(11-22) |

## 7. 아직 확인하지 않은 것

- `0003`에 제조사 서버가 무엇으로 답하는지, 1시간 안에 제조사 서버가 스스로 보내는 메시지가 있는지. 제조사 앱으로 프로비저닝해 핫스팟에서 밤새 캡처해서 확인 예정(현장 절차 13절)
- 실내난방 모드에서도 현재온도 변화 때 `010A`가 오는지(`0102`가 대신하는지)
- 가스 사용량 조회(다이얼 5초)는 조절기 화면 안에서만 동작하고 통신이 없습니다(11-22). 원격 대상이 아닙니다.
- `01FF[0]`의 `0x40`: 예약 가동 먼저 0xC2 / 정지 먼저 0x82. 순서 설정인지 현재 가동 구간인지 확인 필요
- 난방수 설정(`0103`)이 `01FF`의 어느 바이트에 저장되는지
- APK 분석에만 있는 `0103`(난방·온도 관련), `0107`(24시간 예약), `0109`(오류): 오면 신규 로그에 `hint`와 함께 기록됨
- `01FF[0]` 각 비트, `[11]`·`[12]`·`[58~62]`의 의미
- 서버 재시작 직후 조절기가 `0001` 없이 기다리는 동작: 보통 약 130초 뒤 Wi-Fi 재연결, 한 번은 7분 넘게 멈춤(11-22 23 회차). `0001` 없이 `01FF`를 보내며 이어 붙는 경우도 있음(11-22 24 회차). 수집기는 데이터가 전혀 없는 연결만 180초 뒤 닫고(`silent_timeout`), `01FF`로 이어 붙은 연결은 재개된 세션으로 인정. `0001` 유무로 닫았던 이전 판은 재개된 세션을 끊어 조절기가 수 분간 재접속하지 않았음. 닫은 뒤 조절기가 바로 처음부터 접속하는지는 확인 필요
