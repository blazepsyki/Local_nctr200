# NCTR-200 Local

귀뚜라미 보일러 실내 조절기 NCTR-200(Wi-Fi)을 제조사 서버 없이 Home Assistant에서 직접 제어하는 사용자 통합입니다.

조절기는 원래 제조사 서버에 TCP로 접속합니다. 이 통합은 Home Assistant 안에서 같은 프로토콜의 TCP 서버를 열고, 조절기가 그 서버에 접속하도록 Wi-Fi 설정을 바꾼 상태에서 동작합니다. 클라우드를 거치지 않으며(`local_push`), 상태는 조절기가 보내는 보고로 갱신됩니다.

> 제조사와 관계없는 비공식 프로젝트입니다. 프로토콜은 한 대의 조절기를 관찰해서 확인한 것이며, 다른 펌웨어나 모델에서는 다를 수 있습니다.

## 순서

1. HACS로 통합을 설치합니다.
2. 통합을 추가합니다. Home Assistant가 조절기 접속을 기다리기 시작합니다. 이때 조절기는 아직 연결되어 있지 않아도 됩니다.
3. 조절기를 프로비저닝합니다. 조절기의 Wi-Fi 설정에 Home Assistant 주소를 넣는 단계입니다.
4. 조절기가 접속하면 엔티티가 살아납니다.

통합을 먼저 추가하는 이유는 조절기가 프로비저닝 직후 바로 서버에 접속하기 때문입니다. 그때 서버가 기다리고 있어야 첫 접속을 놓치지 않습니다.

## 1. 설치

1. HACS → 오른쪽 위 메뉴 → 사용자 저장소(Custom repositories)
2. 저장소 `https://github.com/blazepsyki/Local_nctr200`, 유형 Integration으로 추가
3. 목록에서 `NCTR-200 Local`을 내려받고 Home Assistant를 다시 시작

HACS 없이 쓰려면 `custom_components/nctr200` 폴더를 Home Assistant 설정 폴더의 `custom_components/` 아래에 복사합니다.

Home Assistant가 조절기 접속을 받을 수 있어야 합니다.
- Docker는 `network_mode: host`를 쓰거나 포트(기본 20000)를 열어 둡니다.
- 같은 포트를 쓰는 다른 프로그램이 있으면 먼저 종료합니다.

## 2. 통합 추가

설정 → 기기 및 서비스 → 통합 추가 → `NCTR-200 Local`

| 항목 | 설명 |
|---|---|
| 허용할 접속 주소(선택) | 이 IP나 네트워크에서 오는 접속만 받습니다. Home Assistant가 속한 LAN 대역(예: `192.168.1.0/24`)이 미리 채워집니다. 비우면 모두 받습니다. Windows 핫스팟을 거치면 조절기가 PC 주소로 보입니다. |
| 포트 | 조절기가 접속할 포트. 기본 20000 |
| 수신 주소 | 기본 `0.0.0.0`(모든 인터페이스) |

설정 화면에 조절기에 넣을 서버 주소가 나옵니다(예: `http://nas.192.168.1.8.nip.io`). 설치한 뒤에도 연결 엔티티의 `provision_server`, `provision_port` 속성과 진단 파일에서 볼 수 있습니다.

## 3. 프로비저닝

### 서버 주소의 형식

조절기는 서버 주소를 항상 DNS로 조회하고, 호스트 이름의 앞 3글자 뒤에 `4`를 끼워 넣습니다. 제조사 값 `igs.krb.co.kr`이 실제로는 `igs4.krb.co.kr`로 조회되는 것도 이 규칙 때문입니다. 그래서 IP를 그대로 넣으면 접속하지 못합니다.

이 통합은 와일드카드 DNS 서비스 nip.io를 씁니다. 버려도 되는 3글자(`nas`)를 앞에 붙여 `http://nas.<IP>.nip.io`를 넣으면, 조절기가 `nas4.<IP>.nip.io`를 조회하고 그 IP로 접속합니다. 로컬 DNS나 공유기 설정은 바꾸지 않아도 됩니다. 다만 조절기가 이 이름을 조회하려면 인터넷에 연결되어 있어야 합니다.

### 조절기를 설정 모드로

조절기 전원을 끈 상태에서 외출 버튼을 5초 누릅니다. 조절기가 설정용 Wi-Fi `krb_set`을 엽니다.

### 방법 A: Home Assistant에서

Home Assistant 기기가 `krb_set`에 직접 연결할 수 있을 때 씁니다. 유선 LAN과 별도로 Wi-Fi 어댑터가 있어야 합니다.

1. Home Assistant 기기를 `krb_set`에 연결하고, 그 무선 어댑터에 IP `192.168.200.2/24`를 직접 지정합니다. 조절기는 IP를 나눠 주지 않습니다.
2. 설정 → 기기 및 서비스 → `NCTR-200 Local` → 구성 → **조절기 프로비저닝**
3. 조절기가 접속할 2.4GHz Wi-Fi 이름과 암호를 넣습니다. 서버 IP는 미리 채워져 있습니다.
4. 보내면 몇 초 안에 `krb_set`이 사라지고, 조절기가 Wi-Fi에 붙은 뒤 Home Assistant에 접속합니다.

Wi-Fi 암호는 한 번만 쓰고 저장하지 않습니다. Home Assistant 기기가 `krb_set`에 연결되어 있지 않으면 아무것도 보내지 않고 오류를 보여 줍니다.

### 방법 B: PC에서 독립 도구로

Home Assistant 기기에 Wi-Fi가 없으면(대부분의 NAS) PC를 씁니다. 필요한 것은 Python 3.11 이상뿐입니다.

1. [`provision.py`](custom_components/nctr200/provision.py)를 내려받습니다. 릴리스 페이지에도 첨부되어 있습니다.
2. PC를 `krb_set`에 연결합니다. 기본 암호는 `krb12345`입니다.
3. PC에 IP를 직접 지정합니다. 조절기는 IP를 나눠 주지 않아서, 그대로 두면 PC가 `169.254.x.x`를 갖고 도구가 "krb_set에 연결되어 있지 않습니다"라고 멈춥니다. Windows에서는 관리자 PowerShell에서 실행합니다(어댑터 이름은 `netsh wlan show interfaces`로 확인).
   ```powershell
   netsh interface ipv4 set address name="Wi-Fi" static 192.168.200.2 255.255.255.0
   ping 192.168.200.1
   ```
4. 실행합니다.
   ```sh
   python provision.py --ssid <Wi-Fi 이름> --server-ip <Home Assistant IP>
   ```
5. 암호를 두 번 입력합니다. 보낼 내용이 나오면 확인하고 `SEND`를 입력합니다.
6. 끝나면 PC의 IP 설정을 되돌립니다.
   ```powershell
   netsh interface ipv4 set address name="Wi-Fi" dhcp
   ```

Windows에서 `python`을 입력했는데 "Python"만 나오고 끝나면 Microsoft Store 실행 별칭이 실행된 것입니다. 설정 → 앱 → 고급 앱 설정 → 앱 실행 별칭에서 `python.exe`, `python3.exe`를 끄거나 Python 실행 파일의 전체 경로로 실행합니다.

PC 무선 어댑터가 `krb_set`에 붙어 있는 동안에는 같은 어댑터로 띄운 Windows 모바일 핫스팟이 꺼집니다. 그래서 `--ssid`에는 집 공유기의 2.4GHz Wi-Fi를 넣는 것이 안전합니다.

| 옵션 | 뜻 |
|---|---|
| `--ssid` | 조절기가 접속할 2.4GHz Wi-Fi 이름 |
| `--server-ip` | Home Assistant 기기의 IP |
| `--port` | 서버 포트. 기본 20000 |
| `--url` | 서버 주소를 직접 지정. 기본 `http://nas.<server-ip>.nip.io` |
| `--password-file` | Wi-Fi 암호를 파일에서 읽음. 없으면 입력받음 |

### 제조사 앱으로 되돌리기

제조사 앱으로 Wi-Fi를 다시 설정하면 서버 주소가 제조사 값으로 돌아갑니다.

## 엔티티

| 엔티티 | 내용 |
|---|---|
| `climate` | 전원(모드 켜짐/꺼짐), 희망온도 다이얼, 현재온도, 운전 모드(프리셋). 다이얼은 온돌 모드에서 온돌 온도(45~85), 그 밖에는 실내 희망온도(10~45) |
| `number` 온돌 온도 | 45~85 |
| `number` 예약 정지 시간, 예약 가동 시간 | 1~24시간, 10~90분. 예약 모드에서 바꾸면 바로 보내고, 다른 모드에서는 값만 저장했다가 예약 프리셋을 고를 때 씁니다. Home Assistant를 다시 시작해도 유지 |
| `number` 온수 온도 | 35~60 |
| `number` 난방수 온도 설정 | 45~85. 조절기가 이 값을 보고하지 않아 마지막 설정값만 표시합니다. 기본으로 꺼져 있음 |
| `sensor` 실내 온도, 난방수 온도 | 상태 보고의 값 |
| `sensor` 운전 모드 | 실내난방·온돌·예약·외출·목욕·온수전용·꺼짐 |
| `binary_sensor` 연결 | 조절기가 접속해 있고 상태 보고가 15분 이내일 때 켜짐. 속성에 프로비저닝할 서버 주소 |
| 진단 `sensor` | 마지막 상태 보고 시각, 연소 단계, 상태 플래그(뒤의 둘은 기본으로 꺼져 있음) |

### 프리셋(운전 모드)

| 프리셋 | 보내는 명령 |
|---|---|
| 실내난방 | 현재 실내 희망온도로 `0102` |
| 온돌 | 현재 온돌 온도로 `0104` |
| 예약 | 예약 정지 시간·가동 시간 엔티티의 값으로 `0108`. 값이 없으면 오류를 보여 주므로 두 값을 먼저 정합니다 |
| 외출 | `0106` |
| 목욕 | `0105` |
| 온수전용 | 현재 온수 온도로 `0114` |

온돌 모드에서 다이얼을 돌리면 온돌 온도만 바뀝니다(`0104`). 그 밖의 모드에서 다이얼을 돌리면 실내난방 모드로 바뀝니다(`0102`). 외출 해제는 다른 프리셋을 고르면 됩니다.

### 서비스

| 서비스 | 내용 |
|---|---|
| `nctr200.set_reservation` | 난방 예약. `stop_hours` 1~24시간 정지, `run_minutes` 10~90분 가동을 반복 |
| `nctr200.set_schedule` | 24시간 예약. `schedule: "00:00-09:00,18:00-24:00"`처럼 30분 단위 구간 |

## 동작 방식

- 명령은 한 번만 보냅니다. 10초 안에 ACK가 없으면 오류로 알리고, 자동으로 다시 보내지 않습니다.
- 조절기는 원격 명령에 ACK만 보내고 바뀐 값을 따로 보고하지 않습니다. 그래서 ACK를 받으면 화면 값을 바로 바꾸고, 약 5분마다 오는 상태 보고로 다시 맞춥니다.
- 전원 켜기에는 ACK 대신 복귀한 모드의 보고가 옵니다. 통합은 이 보고를 응답으로 처리합니다.
- 조절기가 보내는 모든 이벤트에 ACK합니다. ACK를 받지 못하면 조절기는 같은 이벤트를 몇 초마다 다시 보내고 다음 이벤트를 보내지 않습니다.
- 서버가 다시 시작되면 조절기는 식별(`0001`) 없이 다시 접속해 상태 보고부터 보낼 수 있습니다. 이 연결도 받아들입니다. 접속 후 3분 동안 아무것도 보내지 않는 연결은 닫습니다. 그러면 조절기가 다시 접속합니다.
- 접속 후 약 1시간마다 조절기가 연결 확인(`0003`)을 보냅니다. 제조사 서버와 같은 형식(서버 시각과 밀리초)으로 응답합니다. 제조사 서버에서는 이 응답으로 한 번에 끝났습니다. 다른 응답을 보내면 조절기가 10초 간격으로 반복하지만 해는 없습니다.

## 알려진 한계

- 실제 조절기로는 아직 이 통합을 시험하지 않았습니다. 프로토콜은 별도 수집 서버로 확인했습니다.
- 부팅 때 조절기가 nip.io 이름을 조회하므로 인터넷이 필요합니다. 인터넷이 끊긴 상태에서 재부팅하면 접속하지 못할 수 있습니다.
- 운전 모드와 전원 상태는 상태 보고의 플래그에서 읽습니다. 관찰한 값으로 정한 해석이라 처음 보는 조합에서는 틀릴 수 있습니다. 진단의 상태 플래그를 켜 두면 확인할 수 있습니다.
- 목욕과 온수전용은 상태 보고에 나타나지 않고 조절기의 이벤트로만 알 수 있습니다. 조절기가 스스로 끝낸 경우 다음 모드 보고가 올 때까지 이전 표시가 남을 수 있습니다.
- 온돌 온도만 바꾸는 명령(`number`)이 운전 모드도 온돌로 바꾸는지는 아직 확인하지 않았습니다. 바뀐 모드는 다음 상태 보고에 반영됩니다.
- 조절기는 하나만 지원합니다.

## 개발

```sh
uv venv -p 3.14 .local/venv
uv pip install -p .local/venv -r requirements_test.txt
.local/venv/bin/python -m pytest
.local/venv/bin/python -m ruff check .
```

시험은 세 가지입니다.
- `tests/test_hub.py`: 실제 TCP 연결로 가짜 조절기를 붙여 프로토콜을 확인합니다.
- `tests/test_init.py`: 실제 Home Assistant 코어에서 설정 흐름, 프로비저닝 메뉴, 엔티티를 확인합니다.
- `tests/test_provision.py`: 프로비저닝 데이터그램과 독립 도구를 가짜 설정 AP로 확인합니다.
